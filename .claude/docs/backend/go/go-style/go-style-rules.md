# Go Style Guide — индекс правил (gofmt / golangci-lint)

> **Что это.** Сжатый индекс правил Go-стиля: код + формулировка, по разделам. Рабочий вход скиллов —
> review цитирует код в findings. Языко-специфичный concern (аналог Java `JS-*` / Python `PY-*`) — **только
> Go**, префикс `GO-*`. Код-примеры включены (отдельного style-guide нет).
> Коды: `GO-<раздел>.<N>` — рекомендация (MUST), `GO-<раздел>.X<N>` — антипаттерн (MUST NOT).
> Линтеры `errcheck`/`errorlint`/`gocritic`/`revive` ловят часть механики — их нарушения в findings
> не дублируем; фокус на семантике и идиомах.
>
> Стек: `net/http` + `chi/v5`, `sqlc` + `pgx/v5`, `log/slog`, `prometheus/client_golang`, `otel`,
> `gobreaker`, `retry-go/v4`, `semaphore`, `kafka-go`, `go-redis/v9`, `jwt/v5`, `validator/v10`,
> `envconfig`. Ошибки — значения (`apperr.Kind` + `errors.As` + `%w`, см. `error-handling/go/`).

Базовый принцип (`GO-1.1`): **идиоматичный Go предпочтительнее краткого Go** — если выбор между
выразительной идиомой и однострочным трюком, предпочти идиому. Нарушение допустимо только с явным
объяснением выгоды для читаемости или производительности.

---

## 1. Общие принципы

- **GO-1.1.** Предпочитай идиоматичный Go краткому трюку; нарушение любого правила допустимо с явным
  объяснением выгоды.
- **GO-1.2.** `gofmt` и `goimports` запущены до коммита — форматирование не обсуждается вручную.
- **GO-1.3.** `golangci-lint` с конфигом проекта (`errcheck`, `errorlint`, `gocritic`, `revive`) зелёный
  в CI.
- **GO-1.4.** Каждый публичный символ (тип, функция, метод, константа) имеет doc-комментарий; для
  очевидного контракта — минимальный (одна фраза), не пересказ сигнатуры.
- **GO-1.X1.** Внутренние комментарии (`//`) в коде не добавляются — неочевидный WHY выражается именем
  или структурой; закомментированный код удаляется.

---

## 2. Именование

- **GO-2.1.** Пакеты — `lowercase`, одно слово, без символов; имя пакета = имя директории; описывает
  контент, а не «что с ним делают» (`order`, не `orderutils`, не `manageorders`).
- **GO-2.2.** Экспортируемые типы, функции, константы — `MixedCaps`; неэкспортируемые — `mixedCaps`.
- **GO-2.3.** Аббревиатуры — все заглавные или все строчные: `userID`, `HTTPClient`, `URLParser` (не
  `UserId`, `HttpClient`).
- **GO-2.4.** Интерфейсы с одним методом именуются `<Method>er`: `Reader`, `Stringer`, `Handler`;
  интерфейсы с несколькими методами — по роли: `OrderRepository`, `PaymentGateway`.
- **GO-2.5.** Конструкторы — `New<Type>(...)` или `new<Type>(...)` (неэкспортируемый); не `Create`,
  не `Build`.
- **GO-2.6.** Булевые переменные/поля — `isX`, `hasX`, `canX`, `ok`; не голые существительные.
- **GO-2.7.** Имена тестов — `TestFuncName_WhenCondition_ExpectedBehavior`; подтесты через
  `t.Run("when_condition_expected", ...)`.
- **GO-2.8.** Переменные цикла/предикаты — короткие в узком скоупе (`i`, `n`, `ok`) допустимы;
  более широкий скоуп требует говорящего имени.
- **GO-2.X1.** Пакет с суффиксом `util`, `helper`, `common`, `misc` — признак нарушения разбиения;
  перенести в пакет по домену/роли.
- **GO-2.X2.** Имя типа повторяется в именах его методов: `order.OrderCreate()` → `order.Create()`.

---

## 3. Пакеты и импорты

- **GO-3.1.** `goimports` группирует: stdlib / внешние / internal; пустая строка между группами; руками
  не трогать.
- **GO-3.2.** Без dot-импорта (`import . "pkg"`) — нарушает навигацию и линтер.
- **GO-3.3.** Без blank-импорта (`import _ "pkg"`) вне `main` или `init`-пакета; в `main` — с
  `//go:build` тегом или явным комментарием «зачем».
- **GO-3.4.** Не экспортировать из `internal/` вовне пакета-владельца; `internal/` — барьер; нарушение
  ловит компилятор.
- **GO-3.5.** Пакеты-«боги» (>500 строк без чёткой роли) — признак неправильного разбиения; разбить по
  доменной ответственности.
- **GO-3.X1.** Циклические зависимости пакетов — компилятор запрещает; если возникают — пересмотри
  разбиение на пакеты.

## 4. Код и управляющие структуры

- **GO-4.1.** Guard clause (ранний `return err`) вместо вложенных `if err == nil { ... }` — уровень
  вложенности не более 3.

  ```go
  // GO-4.1 PREFER
  if err != nil {
      return fmt.Errorf("load order %s: %w", id, err)
  }
  // продолжение по happy path
  ```

- **GO-4.2.** `switch` без `default` допустим только когда перечислены все варианты exhaustive-enum;
  иначе `default` обязателен (даже если только `panic` или пустое тело с комментарием).
- **GO-4.3.** Не более одного уровня вложенности горутин без явного `sync.WaitGroup` / `errgroup` —
  горутины без ожидания теряются при shutdown.
- **GO-4.4.** `defer` для освобождения ресурсов — сразу после `Open`/`Lock`/`Begin`; не откладывай в
  ветвь `if`.
- **GO-4.5.** Длина функции — ориентир 40 строк до `}`; превышение — сигнал выделить вспомогательную
  функцию.
- **GO-4.6.** `init()` — только для регистрации в глобальном реестре (флаги, prom-метрики через
  `promauto`); бизнес-логика в `init` запрещена.
- **GO-4.X1.** «Голое» `for { select { ... } }` без явного условия выхода и `case <-ctx.Done()` —
  горутина утечёт при отмене контекста.
- **GO-4.X2.** Захват переменной цикла в горутину без копирования (`go func() { use(v) }()` в цикле
  `for v := range`) — классический data race; в Go 1.22+ устранён для range-переменных, но избегай
  паттерн с `for i := 0; ...`.

## 5. Обработка ошибок (идиома значений)

- **GO-5.1.** Ошибки — значения (`func() (T, error)`); классифицировать через `errors.As`/`errors.Is`;
  контекст — `fmt.Errorf("...: %w", err)` с `%w` для сохранения цепочки.
- **GO-5.2.** Каждый возвращённый `error` проверяется явно; `errcheck` ловит проглоченное —
  `_ = doThing()` допустимо **только** при доказуемой безвредности (напр. `io.Closer.Close` в defer
  уже логируется).
- **GO-5.3.** Доменная ошибка — типизированная структура с методом `Kind() apperr.Kind` и контекстом
  (поля, не строки); имя по бизнес-смыслу, не по технике:

  ```go
  type InsufficientFundsError struct {
      CustomerID          string
      Requested, Available int64
  }
  func (e *InsufficientFundsError) Error() string { return fmt.Sprintf(...) }
  func (e *InsufficientFundsError) Kind() apperr.Kind { return apperr.Domain }
  ```

- **GO-5.4.** `panic` — только для невосстановимых программистских ошибок (nil-map write, нарушение
  инварианта при инициализации); бизнес-правило → возврат `error`.
- **GO-5.5.** Единственный `recover()` — в edge-middleware (recover → 500); в core / handler / adapter
  `recover()` нет.
- **GO-5.6.** `errorlint` зелёный: не сравнивай `err == ErrSomething` — используй `errors.Is`; не
  кастуй напрямую без `errors.As`.
- **GO-5.X1.** `fmt.Errorf("%v", err)` или `errors.New(err.Error())` — теряет цепочку и тип; всегда
  `%w`: `fmt.Errorf("context: %w", err)`.
- **GO-5.X2.** `return Struct{}, nil` при фактической ошибке — zero-value скрывает проблему.
- **GO-5.X3.** `panic/recover` как control-flow между слоями (имитация try/catch) — нарушение идиомы.

## 6. Контекст (`context.Context`)

- **GO-6.1.** `context.Context` — первый аргумент каждой функции, имя `ctx`; не хранится в структурах
  (исключение — `http.Request`, где уже внутри).
- **GO-6.2.** `ctx` передаётся во все IO-вызовы: SQL (`pgx`), HTTP-клиент, Kafka, Redis — без контекста
  отменить запрос невозможно.
- **GO-6.3.** `context.WithTimeout` / `context.WithDeadline` — в out-adapter перед IO-вызовом с
  разумным таймаутом; таймаут — из конфига (`envconfig`), не константой в коде.
- **GO-6.4.** Значения в контексте — только cross-cutting data (trace-id, tenant-id, auth-principal);
  не передавай через контекст то, что можно явным аргументом.
- **GO-6.5.** Проверяй `ctx.Err()` / `select { case <-ctx.Done(): }` в долгих циклах — иначе горутина
  не завершится при отмене.
- **GO-6.X1.** `context.Background()` внутри handler/usecase — игнорирует отмену запроса; используй
  переданный `ctx`.
- **GO-6.X2.** Хранение `context.Context` в поле структуры — нарушение идиомы; контекст живёт на
  стеке вызова.

## 7. Конкурентность и горутины

- **GO-7.1.** Горутина, запущенная сервисом, завершается при shutdown: либо через `ctx`-отмену, либо
  через явный `close(stopCh)`; утечка горутин — ошибка.
- **GO-7.2.** `sync.Mutex` / `sync.RWMutex` — для защиты разделяемого состояния; `sync.Map` — только
  для high-contention read-heavy map (большинство случаев — обычная map под mutex).
- **GO-7.3.** Каналы предпочтительнее мьютексов для передачи владения данными между горутинами («не
  коммуницируй через разделяемую память»).
- **GO-7.4.** `golang.org/x/sync/errgroup` для fan-out горутин с обработкой ошибок; не плоди
  `sync.WaitGroup` вручную когда есть готовый инструмент.
- **GO-7.5.** `golang.org/x/sync/semaphore` для булкхеда (ограничение числа параллельных IO-вызовов).
- **GO-7.6.** `go test -race` в CI — обязателен; локально — минимум на integration-тестах.
- **GO-7.X1.** Запуск горутины `go func()` без механизма ожидания завершения в пределах жизни сервиса
  — goroutine leak.
- **GO-7.X2.** Запись в закрытый канал — panic; закрывает только отправитель, не получатель.

## 8. Форматирование и стиль

- **GO-8.1.** `gofmt` / `goimports` обязательны; CI блокирует на `gofmt -l .` с выводом.
- **GO-8.2.** Длина строки — ориентир 100–120 символов (командное соглашение в `golangci-lint` `lll`);
  принудительное выравнивание выравниванием добавляет шум в diff.
- **GO-8.3.** Множественное присваивание в одну строку — только для связанных значений (`x, y := f()`);
  не комбинировать несвязанные переменные ради «краткости».
- **GO-8.4.** Blank lines: одна пустая строка между логическими блоками функции; не более одной подряд.
- **GO-8.5.** `const` блок — для перечислений; `iota` — только внутри одного `const`-блока, не
  перекрывать между блоками.
- **GO-8.X1.** Горизонтальное выравнивание через пробелы (tab-align полей структур/map-литералов) —
  шумит в diff; `gofmt` выравнивает табами и это ок.

## 9. Типы, структуры и интерфейсы

- **GO-9.1.** Малые интерфейсы: один–три метода; большой интерфейс — признак God Object; разбить.
- **GO-9.2.** Принимай интерфейс, возвращай конкретный тип — функции зависят от минимального интерфейса,
  конструкторы отдают конкретную структуру (кроме портов/репозиториев, где нужна мокаемость).
- **GO-9.3.** Встраивание (embedding) — для горизонтального переиспользования метода, не для имитации
  наследования; явная делегация предпочтительнее при неочевидном embedding.
- **GO-9.4.** Иммутабельные value objects — структуры без setter-методов, создаются через конструктор
  с валидацией; полей публичных нет или они `readonly`-по-смыслу.
- **GO-9.5.** Деньги — `int64` (минорные единицы) или `github.com/shopspring/decimal`; **не `float64`**.
- **GO-9.6.** Время — `time.Time` (UTC на входе, timezone-aware на выходе); не строковые форматы внутри
  сервиса.
- **GO-9.X1.** Пустой интерфейс `any` / `interface{}` как способ избежать типизации — снижает
  читаемость и безопасность; использовать только для истинно полиморфных коллекций.
- **GO-9.X2.** `type Alias = Existing` просто чтобы «переименовать» тип без нового поведения — создаёт
  путаницу; используй только для совместимости.

## 10. Тестирование

- **GO-10.1.** Файлы тестов в том же пакете (`package order`) для white-box или в `package order_test`
  для black-box; не мешать в одном файле.
- **GO-10.2.** `github.com/stretchr/testify/require` для fatal-assert (тест прерывается), `assert` —
  для накапливающих проверок; не `t.Fatal`/`t.Error` вместо testify без причины.
- **GO-10.3.** `t.Parallel()` в unit-тестах без разделяемого состояния — ускоряет прогон; в
  integration без изоляции не включать.
- **GO-10.4.** Integration-тесты через `testcontainers-go`; конфигурация — `TestMain` или хелпер
  `setupDB(t)` без глобального стейта.
- **GO-10.5.** Table-driven tests (`tests := []struct{...}{}`) для однотипных сценариев; каждый case
  именован (`name: "when stock empty, returns error"`).
- **GO-10.6.** Моки — интерфейсы, генерированные `mockery` или вручную; не встраивай бизнес-логику в
  мок.
- **GO-10.7.** `go test -race` в CI — обязателен для всех тестов с горутинами.
- **GO-10.X1.** `TestMain` с глобальным состоянием базы без очистки между тестами — нестабильный
  порядок.
- **GO-10.X2.** `time.Sleep` в тесте для синхронизации горутин — заменить на `chan struct{}`, `errgroup`
  или polling с таймаутом.

## 11. Enforcement через golangci-lint

- **GO-LINT-1.** `.golangci.yml` обязателен в корне сервиса; включены минимум: `errcheck`, `errorlint`,
  `gocritic`, `revive`, `gosimple`, `staticcheck`, `unused`, `lll`.
- **GO-LINT-2.** `errcheck` ловит проглоченные ошибки; единственное исключение — `_` с комментарием.
- **GO-LINT-3.** `errorlint` ловит `err == ErrX` вместо `errors.Is` и прямой каст вместо `errors.As`.
- **GO-LINT-4.** `gocritic` / `revive` — стилистические подсказки; `//nolint:gocritic` допустимо с
  обоснованием.
- **GO-LINT-5.** `staticcheck` — семантические проблемы (устаревшие API, неиспользуемые результаты);
  `SA` / `S` / `ST` группы — все включены.
- **GO-LINT-6.** `//nolint:<linter>` без комментария «зачем» — запрещено; CI при наличии bare `//nolint`
  без обоснования — fail.
- **GO-LINT-X1.** Глобальное `nolint:all` или отключение `errcheck` «потому что мешает» — запрещено без
  архитектурного решения.
