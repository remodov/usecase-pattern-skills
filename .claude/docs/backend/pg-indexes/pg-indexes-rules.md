# PostgreSQL Indexes & EXPLAIN — индекс правил

> **Что это.** Сжатый индекс правил `pg-indexes-style-guide.md`: код + формулировка, по разделам. Рабочий вход
> для скиллов — review цитирует код в findings, design сверяется по чек-листу. **Полная версия
> с SQL-примерами, таблицей узлов плана и обоснованием — `pg-indexes-style-guide.md`**; открывай её точечно по разделу.
> Коды: `PG-I-<NNN>` (индексы), `PG-E-<NNN>` (EXPLAIN/runtime). X-кодов нет; запреты вшиты в формулировки.

Базовый принцип: **индекс работает, только если соответствует запросу** — индекс по «частому полю» без учёта селективности и левого префикса не ускоряет.

## 1. Composite-индексы и левый префикс
**MUST:**
- **PG-I-010.** Индекс `(a,b,c)` работает только на левый префикс: `a`, `(a,b)`, `(a,b,c)` — да; `b`, `c` отдельно — нет; `(a,c)` — по `a` ключ, `c` как Filter.
- **PG-I-011.** Порядок написания полей в `WHERE` не важен — оптимизатор переставляет.
- **PG-I-012.** Первым в индексе — поле, по которому чаще `=` в `WHERE`; селективность вторична.
- **PG-I-013.** Поля с диапазонами (`>`,`<`,`BETWEEN`,`LIKE 'x%'`) — последними (после range следующие поля не используются как ключ).
- **PG-I-014.** `ORDER BY` — порядок и направление полей должны совпадать с индексом, иначе отдельная сортировка.

## 2. Селективность
**MUST:**
- **PG-I-030.** Селективность = `distinct/total`; `=`-запрос на >20% таблицы обычно идёт Seq Scan, <5% — почти всегда через индекс.
- **PG-I-031.** Индекс на низкоселективную колонку (`is_deleted`, `status`, страна в одной стране) бесполезен.
- **PG-I-032.** Смотри статистику через `pg_stats` (`n_distinct`, `most_common_freqs`, `null_frac`).
- **PG-I-033.** На SSD `random_page_cost = 1.1`, не дефолтные 4.0 (дефолт под HDD толкает к seq-scan).
- **PG-I-034.** Композитный индекс оживает там, где single-column бесполезен (`status` 62% + `created_at` range = 0.3%).
- **PG-I-035.** После массовой загрузки/UPDATE — `ANALYZE` руками (autovacuum триггерится при ~10%, не успевает на быстрых нагрузках).
- **PG-I-036.** Редкие пиковые значения — увеличь `SET STATISTICS 1000` для колонки + `ANALYZE`.
- **PG-I-037.** Коррелирующие колонки — `CREATE STATISTICS` с зависимостями (PG по умолчанию считает колонки независимыми, завышает в 10–50×).

## 3. Типы индексов
**MUST:**
- **PG-I-020.** `CREATE INDEX` без типа = B-tree — правильный выбор в 80–90% (`=`,`<`,`>`,`BETWEEN`,`LIKE 'prefix%'`,`IS NULL`,`ORDER BY`,`UNIQUE`,composite).
- **PG-I-021.** Hash-индекс почти всегда хуже B-tree — не брать без явной причины.
- **PG-I-022.** GIN — для JSONB / массивов / полнотекста (`jsonb_path_ops` для `@>`); запись медленнее B-tree.
- **PG-I-023.** GiST — для range-типов, геометрии (PostGIS), kNN, EXCLUDE; GIN быстрее на чтение, GiST на запись.
- **PG-I-024.** BRIN — для огромных append-only таблиц с естественной упорядоченностью (логи, метрики); крошечный, range-запросы; деградирует без физической упорядоченности (нужен `CLUSTER`).
- **PG-I-025.** `LIKE '%X%'` — GIN с `pg_trgm` (`gin_trgm_ops`), не B-tree.
- **PG-I-026.** Partial index (`WHERE`-условие в индексе), если индекс нужен только для подмножества — размер в разы меньше, запись быстрее.

## 4. Управление индексами
**MUST:**
- **PG-I-015.** Не создавай `(a)`, если есть `(a,b,c)` — дубликаты занимают место, замедляют запись, путают планировщик.
- **PG-I-016.** `INCLUDE` — для покрывающего индекса (колонки в листьях, не в дереве → Index Only Scan).
- **PG-I-017.** PG не строит индекс по FK автоматически — если по FK джойнят/удаляют родителя, индекс нужен (иначе `DELETE` родителя → seq-scan child).
- **PG-I-018.** Функциональный индекс для регулярных `LOWER()`/выражений в `WHERE`; запросы должны точно совпадать с выражением.
- **PG-I-019.** В продакшен-миграциях — всегда `CREATE/DROP INDEX CONCURRENTLY` (без — `SHARE` lock блокирует запись); не работает в транзакции (миграционный инструмент `runInTransaction="false"`), сломанная попытка → `INVALID` индекс дропнуть и пересоздать.

## 5. EXPLAIN — что просить
**MUST:**
- **PG-E-030.** Для диагностики — `EXPLAIN (ANALYZE, BUFFERS)` (без ANALYZE — только оценка; без BUFFERS не видно кеш/диск). ⚠️ ANALYZE выполняет запрос — для write-операций оборачивай в `BEGIN; … ROLLBACK;`.

> §6 полного гайда — таблица узлов плана (Seq/Index/Bitmap Scan, Nested Loop, Hash/Merge Join, Sort, HashAggregate, Gather, Memoize): когда узел хорош/плох. Смотри в `pg-indexes-style-guide.md`.

## 7. EXPLAIN — что искать в плане
**MUST:**
- **PG-E-031.** Сравни `rows=` (оценка) с `actual rows=`; расхождение 10×+ → статистика устарела (см. `PG-I-035`).
- **PG-E-032.** Реальное время узла = `actual time × loops` (узел с `loops=10000` — это секунды, не мс).
- **PG-E-033.** Важное условие в `Filter:`, а не `Index Cond:` → индекс по полю не используется как ключ; нужен новый индекс или смена порядка полей.
- **PG-E-034.** `Heap Fetches > 0` на Index Only Scan → visibility map устарел, помогает `VACUUM`.
- **PG-E-035.** `Recheck Cond:` — lossy bitmap, на больших выборках теряется эффективность.
- **PG-E-036.** `Batches: > 1` в Hash Join → hash не уместился в `work_mem`, увеличь для сессии.
- **PG-E-037.** `Sort Method: external merge Disk:` → сортировка на диске; увеличь `work_mem` или добавь индекс с нужным порядком.
- **PG-E-038.** Параллельный план (`Gather`/`Workers Launched`) оправдан на больших таблицах; на мелких оверхед worker'ов; `min_parallel_table_scan_size` (8MB).

## 8. Ловушка: count(1) и Index Only Scan на «неподходящем» индексе
**MUST:**
- **PG-E-010.** `SELECT count(1) FROM t WHERE c > X` при индексе `(a,b,c)` — «индекс используется, но не как ключ»: признаки — `Filter:` (не `Index Cond:`), `Heap Fetches: 0`, большое `Rows Removed by Filter`.
- **PG-E-011.** Нужна реальная скорость — индекс по `c` (или `(c, …)`) → план станет Index Scan с `Index Cond: (c > X)`.
- **PG-E-012.** `Heap Fetches > 0` → `VACUUM`, иначе Index Only Scan вырождается в Index Scan с дёрганьем таблицы (может быть медленнее Seq Scan).

## 9. EXPLAIN — что НЕ показывает
**MUST:**
- **PG-E-040.** EXPLAIN — про план одного запроса в моменте; не показывает локи (`pg_locks`/`pg_stat_activity`), autovacuum/wraparound (`pg_stat_user_tables`), memory pressure, replication lag, агрегаты по запросам (`pg_stat_statements`).
