# PostgreSQL Types — индекс правил

> **Что это.** Сжатый индекс правил `pg-types-style-guide.md`: код + формулировка, по разделам. Рабочий вход
> для скиллов — review цитирует код в findings, design сверяется по чек-листу. **Полная версия
> с примерами, таблицами соответствия типов и обоснованием — `pg-types-style-guide.md`**; открывай её точечно по разделу.
> Коды: `PG-T-<NNN>`. X-кодов нет; сводные антипаттерны — `PG-T-08X`/`09X` в разделе 8.

Базовый принцип: **тип в схеме — контракт, пересмотреть на бою дороже, чем выбрать правильно сразу**. `int→bigint`, `varchar(36)→uuid`, `timestamp→timestamptz` — многочасовые миграции с локами, предотвращаемые за 30 секунд при первом DDL.

## 1. Числа
**MUST:**
- **PG-T-010.** PK всегда `bigint`, без вариантов; `int` упрётся в 2.1 млрд, замена — `ALTER TYPE` под ACCESS EXCLUSIVE.
- **PG-T-011.** `smallint` — только для нумератора короткой шкалы (день недели, год); счётчики/лимиты/остатки — `integer`/`bigint`.
- **PG-T-012.** Авто-id (PG10+) — `bigint GENERATED ALWAYS AS IDENTITY`, не `serial`/`bigserial`; `BY DEFAULT` если бывают legacy-импорты.
- **PG-T-013.** Деньги, проценты, налоги, тарифы — `numeric(p, s)`, никогда `real`/`double`/`float` (`0.1+0.2≠0.3`). `numeric(15,2)` валюты, `numeric(20,8)` курсы, `numeric(5,2) CHECK` проценты.
- **PG-T-014.** Тип `money` не использовать — привязан к локали сервера, не хранит код валюты. `numeric` + `currency char(3)`.
- **PG-T-015.** `real`/`double` — только когда уместна неточность (метрики, ML-фичи, embeddings, физика); деньги/учёт — никогда.
- **PG-T-016.** Boolean — это `boolean`, не `smallint 0/1`, не `varchar('Y'/'N')`, не `char(1)+CHECK`.

## 2. Строки
**MUST:**
- **PG-T-020.** Без бизнес-причины ограничивать длину — `text` (`text` и `varchar(n)` хранятся одинаково; `varchar(255)` — наследие MySQL/Oracle).
- **PG-T-021.** `varchar(n)` ставим, когда длина — доменное правило (E.164 phone `varchar(15)`, ISO-страна `char(2)`, валюта `char(3)`, ИНН `varchar(12)`).
- **PG-T-022.** `char(n)` — только для строго фиксированной длины из стандарта; иначе паддинг пробелами ломает `LIKE`/`=`/`length()`.
- **PG-T-023.** Case-insensitive поля (логины, email, теги) — `citext` или functional unique index `lower(...)`, не `LOWER()` в каждом запросе.
- **PG-T-024.** Кластер в `UTF8`, не `SQL_ASCII`.
- **PG-T-025.** Не делить таблицу на «горячие короткие» и «редкий длинный текст» преждевременно — TOAST уже это делает; делить только по измерениям.

## 3. Время
**MUST:**
- **PG-T-030.** Бизнес-время — всегда `timestamptz`, никогда `timestamp without time zone` (хранит UTC, конвертит на I/O-границе).
- **PG-T-031.** На Java `timestamptz` ↔ `Instant` (рекомендуется) или `OffsetDateTime`; `LocalDateTime` — никогда (теряет зону). `date`↔`LocalDate`, `time`↔`LocalTime`.
- **PG-T-032.** `timestamp` без TZ допустим только для «локального времени без момента» (расписание магазина, локальное время вылета); зона — отдельной колонкой.
- **PG-T-033.** Различай `now()`/`transaction_timestamp()` (начало TX) vs `clock_timestamp()` (момент вызова) vs `statement_timestamp()`. `created_at` — обычно `now()`.
- **PG-T-034.** Время в коде — через `DateTimeService` с моком (см. `TS-2`/`TS-7`), не `Instant.now()`; `DEFAULT now()` ок для аудита, не для проверяемых сценариев.
- **PG-T-035.** В SQL для смещений — `INTERVAL` (`now() - interval '15 minutes'`), не магические секунды.

## 4. UUID и идентификаторы
**MUST:**
- **PG-T-040.** UUID — тип `uuid`, никогда `varchar(36)`/`char(36)`/`text` (16 vs 36+ байт, type-safety, нормализация регистра).
- **PG-T-041.** Для PK/FK — UUID v7, не v4 (v4 случаен → random IO в btree; v7 = timestamp+random, последовательные вставки рядом; на 50–100M+ строк 2–5× по скорости вставки).
- **PG-T-042.** UUID v7 генерируем на стороне приложения (`UuidCreator.getTimeOrderedEpoch()`) если PG<18 или нужен id до commit; PG18+ — встроенная `uuidv7()`.
- **PG-T-043.** `bigint IDENTITY` дешевле/быстрее; UUID — когда по делу (распределённые сервисы, публичные URL, id до commit).
- **PG-T-044.** При UUID-PK обязателен индекс по FK в дочерних таблицах (PG не строит автоматически — иначе `DELETE` родителя → seq-scan child).

## 5. Enum, boolean и перечисления
**MUST:**
- **PG-T-050.** Boolean — `boolean` (дубликат `PG-T-016`).
- **PG-T-051.** Выбор ENUM / reference table / `CHECK IN`: известен-редко-меняется-без-атрибутов → `ENUM`; растёт/переименовывается/нужны атрибуты → reference table; технический ≤7 значений → `CHECK IN`. Статусы доменных сущностей — обычно reference table (приобретают `is_terminal`, `sort_order`).
- **PG-T-052.** В коде — типизированный enum, не `String` (Java: typed converter; Python: `StrEnum`) (typed converter для jOOQ).

## 6. JSONB
**MUST:**
- **PG-T-060.** Всегда `jsonb`, `json` — почти никогда (только бит-в-бит сохранение исходного документа).
- **PG-T-061.** Если по полю регулярно фильтруют/сортируют/джойнят — это колонка, не JSON-ключ. `jsonb` — для полиморфных/опциональных/редко-фильтруемых атрибутов.
- **PG-T-062.** Хорошие кейсы: payload события, атрибуты товара по категории, конфиг канала интеграции, кеш-копия внешнего API.
- **PG-T-063.** Плохие кейсы: все основные поля в одном `data jsonb`; поле для поиска в JSONB; «чтобы не писать миграции».
- **PG-T-064.** Операторы: `->` (jsonb по ключу), `->>` (text), `#>`/`#>>` (по пути), `@>` (содержит), `?`/`?|`/`?&` (наличие ключа).
- **PG-T-065.** Для поиска `@>` — GIN-индекс с `jsonb_path_ops`.
- **PG-T-066.** Для запроса по конкретному JSONB-ключу — functional index (`((payload ->> 'event_type'))`), не GIN.
- **PG-T-067.** Не писать в JSONB бинарь/большие тексты/base64 — бинарь `bytea`, текст `text`.

## 7. Массивы и range
**MUST:**
- **PG-T-070.** Массив — только для простых скаляров без идентичности и атрибутов (теги, локали, флаги), до десятков элементов.
- **PG-T-071.** Если у элементов есть атрибуты или они независимо обновляются — отдельная таблица с FK (`jsonb[]` для строк заказа — антипаттерн).
- **PG-T-072.** Семантический интервал — range-тип (`tstzrange`/`daterange`/`int4range`) для тарифов с периодом, бронирований, цен с историей.
- **PG-T-073.** «Интервалы не пересекаются» — `EXCLUDE` constraint (`gist (room_id WITH =, period WITH &&)`), не код приложения (application-lock не защищает от race).
- **PG-T-074.** Range по умолчанию с границей `[)` — включая нижнюю, исключая верхнюю (иначе «14:00-16:00» и «16:00-18:00» пересекаются).

## 8. Антипаттерны (сводный)
**MUST NOT:**
- **PG-T-080.** `varchar(255)` по привычке — `text` или `varchar(n)` по доменному правилу.
- **PG-T-081.** `timestamp without time zone` для бизнес-времени — `timestamptz`.
- **PG-T-082.** `varchar(36)` для UUID — тип `uuid`.
- **PG-T-083.** `float`/`real`/`double` для денег — `numeric(p, s)`.
- **PG-T-084.** `serial`/`bigserial` в новой схеме — `bigint GENERATED ALWAYS AS IDENTITY`.
- **PG-T-085.** `smallint 0/1` / `char(1) Y/N` вместо boolean — `boolean`.
- **PG-T-086.** PG `ENUM` для часто-меняющегося списка — reference table.
- **PG-T-087.** JSONB как «гибкая схема» для основных полей — выносить в колонки.
- **PG-T-088.** Массив там, где должна быть отдельная таблица — таблица с FK.
- **PG-T-089.** Две колонки `valid_from`/`valid_to` вместо range-типа — `tstzrange` + `EXCLUDE`.
- **PG-T-090.** Тип `money` — `numeric` + `currency char(3)`.
- **PG-T-091.** `LocalDateTime` в Java для `timestamptz` — `Instant`/`OffsetDateTime`.
- **PG-T-092.** `Instant.now()` напрямую — `DateTimeService` + мок в тестах.
- **PG-T-093.** UUID v4 для PK — v7.
