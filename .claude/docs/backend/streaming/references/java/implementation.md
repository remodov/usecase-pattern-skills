# Потоковые соединения — реализация на Java (Spring Boot)

Реализация требований `../../spec.md` (`streaming/*`, коды `R-STREAM-*`). Стек по умолчанию: Spring MVC
с `SseEmitter` и `StreamingResponseBody`, Spring WebSocket при двустороннем обмене, Redis для рассылки
между экземплярами.

## 1. Выбор механизма (`streaming/mechanism-matches-exchange`)

| Природа обмена | Решение | Почему не соседнее |
|---|---|---|
| Сервер шлёт, клиент слушает | `SseEmitter` | двусторонний канал добавляет состояние и переподключения без нужды |
| Обе стороны шлют | Spring WebSocket | лента поверх сокета усложняет восстановление |
| Большая выгрузка | `StreamingResponseBody` | сборка в памяти кладёт процесс |

- **AVOID** длинный опрос как «простое решение»: он даёт ту же сложность и худшую задержку.

## 2. Аутентификация и права (`streaming/authenticate-on-handshake`, `authorize-per-subscription`, `long-lived-connections-recheck-rights`)

- Токен проверяется на установлении соединения, до принятия: `HandshakeInterceptor` для сокета,
  обычная цепочка фильтров для потока.
- Подписка на канал проверяется отдельно: доступ к соединению не равен доступу к данным.
- Долгоживущее соединение переучитывает права по сроку жизни токена и закрывается при его истечении.

## 3. Backpressure и лимиты (`streaming/backpressure-is-bounded`, `connection-limit-per-instance`)

```java
SseEmitter emitter = new SseEmitter(Duration.ofMinutes(30).toMillis());
BlockingQueue<Event> queue = new ArrayBlockingQueue<>(QUEUE_LIMIT);

if (!queue.offer(event)) {
    emitter.completeWithError(new SlowConsumerException(subscriptionId));
}
```

- Очередь на получателя ограничена; переполнение закрывает соединение, а не копит память.
- Число одновременных соединений на экземпляр ограничено и наблюдается.

## 4. Поддержание активности (`streaming/heartbeat-and-idle-timeout`)

- Периодический пустой кадр раз в 15–30 секунд: он же вскрывает оборванные соединения.
- Тайм-аут простоя закрывает то, что молчит дольше порога.

## 5. Отмена и ресурсы (`streaming/disconnect-cancels-work`, `no-resources-held-for-connection-lifetime`)

- На `onCompletion` и `onTimeout` отменяется серверная работа и снимается подписка.
- Транзакция и соединение с базой не удерживаются на время потока: данные читаются порциями,
  каждая — своей короткой транзакцией (`pg-runtime/short-transactions`).

## 6. Несколько экземпляров (`streaming/fanout-works-across-instances`)

- Клиент подключён к одному экземпляру, событие рождается на другом: рассылка идёт через Redis pub/sub
  либо через топик брокера, а не через локальный реестр соединений.

## 7. Наблюдаемость (`streaming/connections-observable-without-payloads`)

- Метрики: число соединений, длина очередей, отключения по медленному получателю, возраст соединения.
- Содержимое сообщений в журнал не пишется.

## Чеклист подключения (Java / Spring Boot)

1. Выбран механизм по природе обмена, решение записано в спеке сервиса.
2. Аутентификация на установлении, проверка прав на подписку, переучёт по сроку токена.
3. Ограниченная очередь на получателя и предел соединений на экземпляр.
4. Поддержание активности и тайм-аут простоя.
5. Отмена работы и снятие подписки на закрытии.
6. Рассылка через общий канал, а не локальный реестр.
7. Метрики соединений без содержимого сообщений.
