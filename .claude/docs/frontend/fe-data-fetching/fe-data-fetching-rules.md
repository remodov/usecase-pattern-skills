# Загрузка данных (React + TS, Fetcher + redux-thunk)

> **Что это.** Concern `fe-data-fetching` трека `frontend` (стек React+TS). Single-stack → плоская
> форма: коды + интент + примеры внутри (отдельного style-guide нет). Коды: `FE-DATA-<N>` — обязательно,
> `FE-DATA-X<N>` — антипаттерн. Карта трека — `frontend/_index.md`.
>
> **Это НЕ «как пользоваться fetch».** Concern кодифицирует **сквозную сетевую архитектуру проекта** — несколько
> слоёв с явными контрактами, а не вызов библиотеки:
> 1. **Транспорт** — типизированные хелперы `get/post/put` (`~/fetchers/utils`) поверх `fetch`, возвращающие
>    `HttpResponse<T>` с полем `.parsedBody`; `validateResponse` на не-2xx бросает **типизированный** `RequestError`
>    (несёт `statusCode` + сериализованные поля `error`/`error_uri`/`error_description`). Авторизация (Bearer-токен)
>    и базовый URL (`contextRoot` + per-service host) подставляются **централизованно**, не в каждом вызове.
> 2. **Доменные fetcher'ы** — узкие функции на ресурс/действие (`fetchClientById`), инкапсулируют метод/URL; URL —
>    только из билдеров `~/utils/endpoints`.
> 3. **Thunks** (`redux-thunk`) — каждый async-вызов обёрнут **`middlewareHandler(dispatch, requestStatusAction,
>    handler, errorHandler?)`** — единый контракт жизненного цикла и ошибок (см. §3).
> 4. **Состояние** — результат кладётся в RTK slice; статус операции — в карте `requestStatuses` (см. `fe-state`).
>
> RTK Query baseQuery (`createBaseQuery`, `src/store/rtk-services/api.ts`) — альтернатива для новых эндпоинтов;
> контракты статусов/типизации обязательны так же. Связанные: `fe-component` (`FE-CMP-X1`), `fe-state` (`FE-ST-3`),
> `fe-forms` (submit зовёт thunk, использует его возвращаемое значение).

## 1. Где живут запросы (не в компоненте)
**MUST:**
- **FE-DATA-1.** Сетевой запрос инициируется через **thunk**, а не из тела/JSX презентационного компонента; компонент диспатчит thunk и читает результат из стора (cross-ref `FE-CMP-X1`, `fe-state`).
- **FE-DATA-2.** Запуск загрузки на маунте/смене параметров — `useEffect`, который **диспатчит thunk** (`dispatch(fetchClients())`), а не вызывает `fetch`/fetcher напрямую внутри эффекта.
- **FE-DATA-3.** Доменная логика запроса (URL, маппинг ответа, цепочка диспатчей) живёт в слое thunk+fetcher и переиспользуется, а не копируется по компонентам.

**MUST NOT:**
- **FE-DATA-X1.** `fetch`/`axios`/прямой вызов fetcher внутри JSX или тела презентационного компонента (cross-ref `FE-CMP-X1`) — выноси в thunk+fetcher.
- **FE-DATA-X2.** Запрос в `useEffect` компонента в обход thunk (минуя `middlewareHandler`, статусы и обработку ошибок) — размазанная сетевая логика без контракта.

## 2. Слой транспорта и доменных fetcher'ов
**MUST:**
- **FE-DATA-4.** Сетевой вызов идёт через типизированные хелперы `get/post/put` (`~/fetchers/utils`) / доменные fetcher-функции; компонент и thunk не конструируют `Request`/`fetch` руками.
- **FE-DATA-5.** URL берётся **только из `~/utils/endpoints`** — константой или функцией-билдером (`getEndpointClientById(id)`); параметры подставляются билдером, не конкатенацией строк.
- **FE-DATA-6.** Доменный fetcher — узкая функция на ресурс/действие (`fetchClientById`), возвращающая типизированный результат; HTTP-детали (метод, заголовки, базовый url, авторизация) инкапсулированы в транспортном слое, а не повторяются в каждом fetcher'е.
- **FE-DATA-13.** Результат читается из типизированного `HttpResponse<T>.parsedBody` (парсинг и валидация статуса — в транспорте); не-2xx уже превращён транспортом в **типизированный** `RequestError` (со `statusCode` и сериализованными полями) — доменный код ловит/пробрасывает его, а не парсит тело и коды вручную.

**MUST NOT:**
- **FE-DATA-X3.** Хардкод URL/пути (`'/api/clients/' + id`) в компоненте, thunk или fetcher вместо `~/utils/endpoints`.
- **FE-DATA-X4.** Дублирование одного и того же запроса разными инлайн-вызовами вместо единой доменной fetcher-функции.
- **FE-DATA-X9.** Ручной `response.json()`/разбор HTTP-статуса/заголовков в доменном коде в обход транспорта (`get/post/put` + `validateResponse`) — дублирование контракта ошибок и типов.

## 3. Контракт thunk: middlewareHandler, статусы и ошибки
**MUST:**
- **FE-DATA-7.** Каждый async-вызов в thunk обёрнут **`middlewareHandler(dispatch, requestStatusAction, handler)`**. Контракт: перед запросом диспатчится `RequestState.PENDING`, при успехе — `FULFILLED`, при исключении — `REJECTED` (с приложенной ошибкой). Жизненный цикл операции — `INITIALIZED → PENDING → FULFILLED | REJECTED` (enum `RequestState`), а не самописный булев `isLoading`.
- **FE-DATA-14.** При исключении `middlewareHandler` **сам** сериализует ошибку, диспатчит её в глобальный `error-slice` (`addError`) и логирует централизованно (`BrowserLogger`) — доменный thunk не дублирует обработку; кастомная пост-обработка идёт через опциональный `errorHandler`, а не через свой `try/catch` поверх.
- **FE-DATA-15.** `middlewareHandler` **никогда не реджектит** (всегда резолвится) и **возвращает значение** `handler`'а — thunk прокидывает его наверх, чтобы вызывающий код мог среагировать на результат (например, после submit перейти на роут по полученному id). Проверяй результат на `undefined`, а не оборачивай вызов в свой `catch`.
- **FE-DATA-8.** Загрузка и ошибка **видны в UI**: компонент рендерит loading/error по статусу операции из селектора (спиннер/скелетон + сообщение), а не «пустой экран до появления данных».

**MUST NOT:**
- **FE-DATA-X5.** Свой `try/catch` поверх `middlewareHandler` или пустой `catch {}` — дублирует/ломает контракт (двойной диспатч ошибки или молчаливое проглатывание).
- **FE-DATA-X6.** Запрос без `requestStatusAction` (операция не отражена в `requestStatuses`) — нельзя отличить загрузку от пустого результата и от ошибки.

## 4. Типизация, отмена и параллельность
**MUST:**
- **FE-DATA-10.** Ответ типизирован дженериком — `get<Client[]>(url)`; форма данных описана типом, без `any` в ответе и пэйлоаде диспатча.
- **FE-DATA-11.** Устаревшие ответы при гонках игнорируются/отменяются: `AbortController`/`signal` или проверка актуальности параметров перед записью в стор — последний инициированный запрос побеждает, а не последний пришедший.
- **FE-DATA-12.** Несколько независимых запросов запускаются параллельно через `Promise.allSettled` (а не последовательным `await` в цикле); каждый результат обрабатывается по `fulfilled`/`rejected` (частичный успех — норма: одна упавшая enrichment-подгрузка не роняет весь список).

**MUST NOT:**
- **FE-DATA-X7.** `any` (или нетипизированный ответ) на выходе fetcher'а — теряется контроль формы данных вниз по стору и вью.
- **FE-DATA-X8.** Игнор гонок: ответ устаревшего запроса перезаписывает свежий стейт (нет отмены/проверки актуальности) — мерцание и неверные данные.

## 5. Чеклист подключения (React + TS, Fetcher + thunks)
1. Запрос — в thunk, не в компоненте; компонент диспатчит thunk, читает результат из стора (`fe-state`).
2. Вызов через `get/post/put` (`~/fetchers/utils`) / доменный fetcher; URL только из `~/utils/endpoints`; читаешь `.parsedBody`, не парсишь вручную.
3. Thunk обёрнут `middlewareHandler` (PENDING→FULFILLED/REJECTED); свой `try/catch` поверх не нужен — ошибка, лог и `error-slice` уже в контракте.
4. Возвращаемое значение thunk'а используется вызывающим кодом (например, навигация после submit); статус операции виден в UI.
5. Ответ типизирован `get<T>` без `any`; гонки отменяются (`AbortController`); параллель — `Promise.allSettled`.
6. Новый эндпоинт можно завести через RTK Query baseQuery (`createBaseQuery`) как альтернативу — статусы и типизация обязательны так же.
