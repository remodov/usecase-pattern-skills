# Управление состоянием (React + TS, Redux Toolkit)

> **Что это.** Concern `fe-state` трека `frontend` (стек React+TS, **Redux Toolkit**). Single-stack → плоская
> форма: коды + интент + примеры внутри (отдельного style-guide нет). Коды: `FE-ST-<N>` — обязательно,
> `FE-ST-X<N>` — антипаттерн. Карта трека — `frontend/_index.md`.
>
> **Реализация под проект:** Redux Toolkit (`createSlice`/`configureStore`), `react-redux` 8 (типизированные
> `useSelector`/`useDispatch`), `redux-thunk`. Server-state наполняется через thunks (см. `fe-data-fetching`).
> Связанные: `fe-data-fetching` (запросы/thunks/request-status), `fe-component` (вью не лезет в стор напрямую за
> бизнес-логикой), `fe-forms` (локальное состояние формы — в Formik, не в сторе).

## 1. Разделение local UI-state и доменного состояния
**MUST:**
- **FE-ST-1.** Эфемерное UI-состояние (открыт ли popup, активный таб, ввод в неотправленной форме) держи **локально** (`useState`/`useReducer`/Formik), не в глобальном сторе.
- **FE-ST-2.** В Redux-сторе — только то, что переживает размонтирование компонента или нужно нескольким несвязанным веткам дерева (доменные сущности, текущий пользователь, глобальные фильтры).
- **FE-ST-3.** Server-data в сторе сопровождается **статусом операции** в виде enum `RequestState` (`INITIALIZED → PENDING → FULFILLED | REJECTED`, поле + опциональная ошибка), а не самописного `isLoading`-флага. Это кеш с состоянием загрузки, наполняемый thunk'ом (`fe-data-fetching`), а не «вечная истина».
- **FE-ST-12.** У slice — **карта статусов по операциям** (`requestStatuses: { fetchList, fetchById, edit, create }`), каждая операция инициализируется `initRequestStatus`; не один общий флаг на весь slice. UI и thunk обращаются к статусу конкретной операции.
- **FE-ST-13.** Списки с пагинацией хранятся единой формой list-state (`items` + `offset`/`limit` + `isListEnd`); догрузка следующей страницы **дополняет** (`concat`), первая/сброшенная — **заменяет**; решение append-vs-replace — в редьюсере по сравнению offset'ов, не в компоненте.

**MUST NOT:**
- **FE-ST-X1.** Локальный UI-флаг (hover, фокус, раскрытие аккордеона) в глобальном сторе — лишние ре-рендеры и связность.
- **FE-ST-X7.** Один общий `isLoading`/`error` на весь slice при нескольких операциях — статусы параллельных запросов затирают друг друга; нужна карта по операциям (`FE-ST-12`).

## 2. Структура slice и иммутабельность
**MUST:**
- **FE-ST-4.** Один slice — одна доменная область (`app`, `user`, `clients`, `error`); `createSlice` с типизированным `initialState`, редьюсеры через `PayloadAction<T>`.
- **FE-ST-5.** Мутации состояния — **только внутри редьюсеров slice** (Immer-черновик); за пределами reducer'а состояние иммутабельно.
- **FE-ST-6.** Изменение стора — через диспатч экспортированных `actions` slice (или thunk'ов), не прямой записью в объект состояния.

**MUST NOT:**
- **FE-ST-X2.** Мутация объекта состояния вне редьюсера (`state.items.push(...)` в компоненте/селекторе/thunk вне `createSlice`) — RTK Immer работает только внутри reducer'а.
- **FE-ST-X3.** «God-slice», в который свалены несвязанные домены; раздели по областям.

## 3. Селекторы и производные данные
**MUST:**
- **FE-ST-7.** Доступ к стору — через **именованные селекторы** (`appSelectors.contextRootSelector`), а не инлайн-стрелки `useSelector(s => s.app.x)` по всему дереву; селекторы — единая точка знания о форме стора.
- **FE-ST-8.** Производные данные (фильтрация/агрегация/счётчики) вычисляй в селекторе (при необходимости — мемоизированном), а не дублируй в сторе отдельным полем.
- **FE-ST-9.** `useSelector` возвращает **узкий срез**, нужный компоненту, а не весь slice; новые объекты/массивы в селекторе мемоизируй, чтобы не ломать referential equality.
- **FE-ST-14.** Селекторы — слоистые: базовый (`defaultXSelector = s => s.x`) → производные поверх него. Кросс-slice **джойны** и тяжёлые деривации (например, склейка двух коллекций по ключу) — через `createSelector` (`reselect`) для мемоизации, а не сборка нового массива на каждый рендер.

**MUST NOT:**
- **FE-ST-X4.** Дублирование источника правды: одно и то же хранится в двух полях/срезах и рассинхронизируется. Один источник + селектор.
- **FE-ST-X5.** Вычисление производных данных в компоненте на каждом рендере вместо селектора (размазанная бизнес-логика, cross-ref `fe-component`).

## 4. Типизация и подключение
**MUST:**
- **FE-ST-10.** Типобезопасные хуки: `RootState`/`AppDispatch` из `configureStore`, прокинутые в типизированные `useAppSelector`/`useAppDispatch`; никаких `any` в стейте и пэйлоадах.
- **FE-ST-11.** Side-effect'ы (запросы, цепочки диспатчей) — в thunk'ах (`fe-data-fetching`), не в редьюсерах; редьюсер чист и синхронен.
- **FE-ST-15.** Store собирается из корневого редьюсера фабрикой (`rootReducer()` + `configureStore`). Если приложение монтируется в host (микрофронт), единый инстанс store **переиспользуется** между маунтами (singleton), а не пересоздаётся каждый раз; ослабление middleware (например, отключение `serializableCheck`) — осознанное точечное решение с причиной, а не «чтобы не ругалось».

**MUST NOT:**
- **FE-ST-X6.** Асинхронщина/запрос/`Date.now()`/random внутри редьюсера — редьюсер должен быть детерминированным и чистым.
- **FE-ST-X8.** Пересоздание store на каждый mount в host-режиме (теряется состояние, дублируются подписки) — переиспользуй существующий инстанс (`FE-ST-15`).

## 5. Чеклист подключения (React + Redux Toolkit)
1. UI-эфемерида — локально; в сторе — только доменное/разделяемое состояние.
2. Slice по домену, `PayloadAction<T>`, мутации только в редьюсерах (Immer).
3. Server-data: enum `RequestState` + карта `requestStatuses` по операциям (не один флаг); списки — list-state с append/replace.
4. Доступ через слоистые именованные селекторы; кросс-slice джойны — `createSelector` (`reselect`); срез узкий.
5. Типизированные `useAppSelector`/`useAppDispatch`, без `any`; эффекты — в thunk'ах; store-инстанс переиспользуется в host-режиме.
