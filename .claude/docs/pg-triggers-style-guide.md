# PostgreSQL Triggers Style Guide

Когда триггеры/хранимые процедуры оправданы и когда — нет. Кодами `PG-TR-NNN` ссылается скилл `ucp-pg-schema-review`.

Базовый принцип: **бизнес-логика в коде приложения, не в БД.** Триггер скрывает поведение от разработчика, привязан к движку, тестируется только через интеграционные тесты с PG.

---

## 1. Default position

### `PG-TR-001` — Бизнес-логика живёт в коде приложения

В коде она тестируется unit'ами, видна в IDE, версионируется в git с фичей, откатывается релизом.

### `PG-TR-002` — Триггер — невидимая логика

Разработчик пишет `UPDATE` без определённого поля и удивляется, что триггер тихо обновил.

### `PG-TR-003` — Это не значит «триггеры зло»

— есть редкие сценарии (см. §3). Default — без них.

## 2. Что НЕ надо делать триггерами

### `created_at` / `updated_at`

### `PG-TR-010` — Триггер для `updated_at = now()` — антипаттерн

Используй `DEFAULT now()` в DDL и обновляй из приложения:
```sql
-- хорошо
created_at  timestamptz NOT NULL DEFAULT now(),
updated_at  timestamptz NOT NULL DEFAULT now()

-- в коде:
UPDATE order_doc SET status = ?, updated_at = now() WHERE id = ?;
```

### Денормализация (счётчики, агрегаты)

### `PG-TR-020` — Триггер `AFTER INSERT/DELETE` для обновления `count`/`sum` — терпимо, но не идеально

Альтернативы:
- Materialized view с refresh.
- Read Model в коде через event-handler (UCP Level 2).
- Расчёт on-the-fly при чтении.

Триггер удобен для мгновенной консистентности, но цена — невидимая логика.

### Валидация инвариантов

### `PG-TR-040` — CHECK constraint > триггер

Простые инварианты — через `CHECK`. EXCLUDE для непересечений интервалов. Сложные (зависящие от других строк) — в коде с `SELECT FOR UPDATE`.

```sql
-- хорошо: CHECK
ALTER TABLE order_doc ADD CONSTRAINT ck_order_total_positive CHECK (total_amount >= 0);

-- хорошо: EXCLUDE
EXCLUDE USING gist (room_id WITH =, period WITH &&)

-- терпимо: триггер для сложного инварианта
CREATE TRIGGER tr_doctor_oncall_check ... FOR EACH ROW EXECUTE FUNCTION ...;
```

## 3. Когда триггер действительно оправдан

### `PG-TR-050` — Только в этих случаях:

1. **Compliance** — медицина, банк, регулируемая отрасль. Audit-триггер гарантирует «не пропустим ни одно изменение».
2. **Существующая система с PG как источником истины**, через который ходят несколько приложений. Триггер — единственный способ обеспечить инвариант.
3. **Денормализация с критичной мгновенной консистентностью** (точный `count` после COMMIT, не «когда-то догонит»).
4. **Защита от ручного UPDATE через psql** — devops лезут руками, триггер защитит схему.

## 4. Хранимые процедуры (FUNCTION / PROCEDURE)

### `PG-TR-060` — В современном Java/Spring — почти никогда не нужны

Что обычно делают процедурами:
- Сложная транзакция → `@Transactional` в Spring.
- Bulk-логика → `INSERT INTO ... SELECT ...` без процедуры.
- Производительность → редко выигрывает у app-кода с jOOQ batch.

### `PG-TR-061` — Где процедура оправдана:
- Тяжёлые SQL-операции, где network round-trip между PG и app существенен (миллионы строк, сложные join'ы).
- ETL, который читает гигабайты, агрегирует, пишет.

### `PG-TR-062` — PG procedures (PG11+) умеют commit/rollback внутри

в отличие от functions. Полезно для batch-job'ов с промежуточными commit'ами.

### `PG-TR-063` — Альтернатива — `@Scheduled` + батчированный код в Java

Та же логика, тестируется обычно, видно в репо.

## 5. Стоимость триггеров

### `PG-TR-070` — Триггер увеличивает время записи
- `BEFORE` — выполняется до записи, может изменить значения.
- `AFTER` — после, только чтение.
- `FOR EACH ROW` — на каждую строку (медленно для bulk).
- `FOR EACH STATEMENT` — один раз на statement (быстрее).

### `PG-TR-071` — На bulk операциях `FOR EACH ROW` особенно дорог

`INSERT INTO target SELECT FROM source` 1M строк → триггер выполнится 1M раз.

### `PG-TR-072` — Триггеры могут стать причиной deadlock

Если триггер обновляет другую таблицу, порядок локов меняется недетерминированно.

## 6. Документирование триггера

### `PG-TR-080` — Каждый триггер обязан быть документирован в миграции — что и зачем:

```sql
-- ПОЧЕМУ: compliance-требование (152-ФЗ ст.16) — каждое изменение PII логируется в audit.
-- БЕЗ ТРИГГЕРА: разработчик может забыть logEvent() в новом коде → пропуск в audit.
CREATE TRIGGER tr_customer_pii_audit
AFTER UPDATE OF email, phone, document_number ON customer
FOR EACH ROW EXECUTE FUNCTION log_pii_change();
```

### `PG-TR-081` — Тесты на триггерную логику — через интеграционные тесты в Spring

(Testcontainers PostgreSQL). Логика проверяется через INSERT/UPDATE и assertion на итоговое состояние.

## 7. Антипаттерны

`PG-TR-090` Триггер для `updated_at` — лучше явно в коде.

`PG-TR-091` Триггер для бизнес-валидации (`if order.total < 1000 then disallow`) — должно быть в Java-сервисе.

`PG-TR-092` Триггер, отправляющий `NOTIFY` или вызывающий внешний HTTP — связь с приложением скрыта.

`PG-TR-093` Сложная цепочка триггеров (`A -> trigger -> B -> trigger -> C`) — отлаживать ад.

`PG-TR-094` Stored procedure для логики, которую можно сделать в коде — лишние миграции, нет тестов.

`PG-TR-095` Триггер `BEFORE INSERT` модифицирующий `NEW.*` без явного документирования — разработчик удивляется, что INSERT записал не то, что отправил.

`PG-TR-096` Триггер без описания «почему» в миграции — через год никто не помнит.

---

## Чек-лист на ревью

- [ ] Бизнес-логика в коде, не в триггерах.
- [ ] `updated_at` обновляется явно из кода или через `DEFAULT now()`, не триггером.
- [ ] Денормализованные счётчики — через MV, Read Model или код, не триггер (если только не критична мгновенная консистентность).
- [ ] Audit-триггер — только для compliance-требований.
- [ ] CHECK constraint предпочтителен триггеру для простых инвариантов.
- [ ] EXCLUDE constraint для непересечений, не триггер.
- [ ] Хранимые процедуры — только для тяжёлых ETL с большим IO между PG и app.
- [ ] Все триггеры задокументированы (комментарий «почему» в миграции).
- [ ] Тесты на триггерную логику есть в интеграционных тестах.
