# Формат findings и протокол локализации

Общий регламент для всех code-review скиллов (`ucp-java-style-review`, `ucp-api-review`, `ucp-auth-review`, `ucp-ddd-tactical-review`, `ucp-pattern-review`). Описывает, как локализовать нарушение в файле и как оформить замечание. Каждое правило имеет код (`RFF-1`, `RFF-2`, …) — review-скиллы могут ссылаться на эти коды.

Документ применим только к ревью кода, где finding имеет конкретное место в файле. Для ревью документов / спек (например, `ucp-spec-review`), где локализация идёт по разделам, регламент **не** применяется.

## §1 Локализация finding

`RFF-1` **Перед формированием каждого finding обязательно сделай `Read` файла** с явными `offset` / `limit` вокруг ожидаемого места. Никаких других источников номеров строк не существует.

`RFF-2` **Запрещено** определять номер строки:
- по выдаче `git diff` (там показан контекст и hunk-заголовки, не реальная нумерация в файле);
- сложением «количество добавленных строк» с `@@ -A,B +C,D @@`;
- по памяти после прочтения куска файла раньше в диалоге;
- по результатам `Grep` без последующего `Read` (Grep даёт строку, но между прочтениями файл мог измениться).

`RFF-3` Номер строки бери **из выдачи Read** — это число в префиксе `cat -n` (формат `<номер>\t<содержимое>`). Содержимое строки скопируй **дословно** — оно пойдёт в обязательное поле `Строка`.

`RFF-4` **Fallback при неуверенности.** Если после Read-проверки ты не уверен в номере (несколько кандидатов, файл за это время менялся, строка переехала из-за форматирования) — **не выдумывай номер**. Вместо `<Файл>:<Линия>` пиши только `<Файл>` и в поле `Строка` приводи фрагмент-цитату; читатель найдёт по поиску. Ошибочный номер хуже отсутствующего: он подрывает доверие ко всему отчёту.

`RFF-5` Не ссылайся на «ещё одну такую же проблему ниже» без отдельного Read для каждого вхождения. Каждое вхождение = отдельный finding с собственной Read-проверкой.

## §2 Формат single-line finding

`RFF-6` Single-line finding оформляется так:

```
<ПутьФайла>:<СтрокаНомер>  [<КодПравила>]  <Серьёзность>
  Строка: <дословное содержимое строки, как её показал Read>
  Проблема: <однострочное описание>
  Почему: <какое правило, краткой цитатой>
  Как исправить: <конкретное предложение, желательно сниппет кода>
```

`RFF-7` Поле `Строка` обязательно. Если номер съехал, читатель сразу видит несоответствие и не теряет время. Без `Строка` finding невалиден.

`RFF-8` `<КодПравила>` — код из соответствующего style guide (например `JS-2.6`, `R-UC-1`, `AUTH-15`). Если правило прямо не закодировано — пиши код раздела (`§3.4`).

## §3 Формат range finding

`RFF-9` Если finding покрывает диапазон строк (вложенные условия, большая лямбда, длинный метод) — пиши `<ПутьФайла>:<Start>-<End>` (например `Foo.java:42-58`) и в поле `Строка` приводи две цитаты с префиксами:

```
<ПутьФайла>:<Start>-<End>  [<КодПравила>]  <Серьёзность>
  Строка:
    Start (42): <первая строка диапазона дословно>
    End   (58): <последняя строка диапазона дословно>
  Проблема: <…>
  Почему: <…>
  Как исправить: <…>
```

`RFF-10` Обе границы диапазона должны быть подтверждены `Read` — и `Start`, и `End`. Если только один из концов проверен — это single-line finding, не range.

## §4 Уровни серьёзности (универсальная шкала)

`RFF-11` Три уровня, общие для всех code-review скиллов:

- **Критично** — нарушение, ломающее корректность, инвариант или базовую читаемость в моменте. Требует исправления до merge.
- **Предупреждение** — отклонение от конвенции, не ломающее корректность, но создающее долговой шум (нейминг, неявные модификаторы, отсутствие маркеров). Желательно исправить.
- **Замечание** — улучшение / придирка / стилистическое предложение. Не блокирует merge.

`RFF-12` Конкретные примеры, что относится к каждому уровню — задаются доменно-специфичным style guide и review-скиллом. Этот документ закрепляет только **шкалу**, не **наполнение**.

## §5 Резюме отчёта

`RFF-13` В конце отчёта обязательно — резюме:

```
Резюме:
  Критично:        <n>
  Предупреждение:  <n>
  Замечание:       <n>
  Вердикт: <соответствует | незначительные отклонения | требует доработки>
```

`RFF-14` Вердикт выбирается так:
- `соответствует` — нет findings уровня **Критично** и **Предупреждение**;
- `незначительные отклонения` — есть **Предупреждение**, нет **Критично**;
- `требует доработки` — есть хотя бы один **Критично**.

## §6 Границы скилла

`RFF-15` Review-скилл **код не модифицирует**. Только сообщает. Предложения в поле `Как исправить:` — текстовые / сниппеты, без редактирующих tool-вызовов.

`RFF-16` Если в итоге не нашлось ни одного finding — скажи это явно и сошлись на то, какие разделы style guide ты покрыл. Молчаливый «всё хорошо» — плохой отчёт.
