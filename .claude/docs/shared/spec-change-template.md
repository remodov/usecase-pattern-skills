# Изменение спецификации: формат

Спека описывает контекст **как есть сейчас**. Причина, по которой он стал таким, в ней не живёт: после правки
остаётся результат, а решение и его альтернативы испаряются. Change-документ закрывает этот зазор — он
единица работы над живущим сервисом, живёт, пока изменение делается, вливается в спеку и уходит в архив.

Парные скиллы: `ucp-spec-change` (написать и влить) ↔ `ucp-spec-change-review` (гейт, коды `SC-*`).
Формат самой спеки — `usecase-spec-template.md`; здесь описан только документ изменения.

## Когда нужен

- Меняется контракт: команда, событие, роль, инвариант, граница контекста, НФТ.
- Добавляется Use Case или агрегат в существующий контекст.
- Меняется уровень зрелости (1 → 2, 2 → 3).

Не нужен: опечатки, переформулировки без смены смысла, заполнение пропущенного раздела — это правка спеки
напрямую. Новый сервис с нуля — `ucp-spec-design`, не change.

## Раскладка

```
docs/spec/
  <service>-spec.md
  aggregates/<unit>.md
  changes/
    <YYYY-MM-DD>-<slug>.md          # активные
    archive/<YYYY-MM-DD>-<slug>.md  # влитые
```

Один change — один файл — одно изменение. Два несвязанных изменения в одном документе разъезжаются при
слиянии и делают историю нечитаемой.

**Frontmatter** (минимальный, как у спеки):

```yaml
context: order-service
change: cancel-after-shipping
status: proposed | approved | in-progress | merged
level: 2
```

## Секции

Нумерация сквозная 1–7. Ссылки на разделы спеки — по **имени** (`«Команды · CancelOrder»`), не по номеру.

| № | Раздел | Что внутри |
|---|---|---|
| 1 | **Зачем** | проблема или требование своими словами; что ломается сегодня; рассмотренные альтернативы и почему выбрана эта. Это единственное место, где живёт «почему» — в спеке его после слияния не будет |
| 2 | **Что меняется** | таблица `файл · раздел · было · станет`. Каждая строка указывает на конкретный раздел конкретного файла спеки |
| 3 | **Влияние** | класс изменения (`breaking` / `compatible` / `semantic-break`) + поимённо затронутые UC, команды, события, контракты и их потребители |
| 4 | **Миграция** | стратегия под класс: expand-contract для API, `vN+1` для событий, ADR для смены термина Ubiquitous Language. Для `compatible` — строка «не требуется» |
| 5 | **Задачи** | вертикальными срезами: каждый срез собирается и проверяется отдельно, каждый называет `ucp-*` скилл, а не прозу |
| 6 | **Критерии приёмки** | Given / When / Then на новое поведение и на путь ошибки. При слиянии переезжают в «Критерии приёмки» спеки |
| 7 | **Слияние** | чек-лист: какие разделы спеки обновлены, дата, куда уходит документ |

## Класс изменения

Определяет раздел «Миграция» и то, что вообще можно делать.

| Класс | Что это | Обязательная миграция |
|---|---|---|
| **compatible** | старые потребители продолжают работать без правок: новое опциональное поле, новая команда, новое событие | не требуется |
| **breaking** | старый потребитель сломается: удалено/переименовано поле, изменён тип, убрана команда, изменён обязательный контракт | expand-contract (добавить новое → перевести потребителей → удалить старое), для событий — `vN+1` рядом со старой версией |
| **semantic-break** | контракт формально прежний, а смысл другой: то же поле стало значить другое, статус сменил условие перехода | ADR + явное уведомление потребителей; чинится только договорённостью, не кодом |

**semantic-break опаснее breaking**: компилятор и схема молчат, потребитель узнаёт о нём в проде. Если
изменение хоть немного semantic — классифицируй как semantic-break, а не compatible.

## Слияние и архив

Слияние — отдельный шаг, а не побочный эффект правки:

1. Разделы спеки из «Что меняется» обновлены — все до одного.
2. Критерии приёмки переехали в «Критерии приёмки» спеки.
3. Ubiquitous Language пополнен, если появились термины.
4. В документе `status: merged` и дата.
5. Файл переехал в `changes/archive/`.

Архив — не свалка: по нему отвечают на вопрос «почему здесь так», который спека не покрывает. Удалять
документы из архива нельзя — они и есть память решений.

## Границы

- Change-документ **не заменяет спеку**: после слияния источник правды — спека, документ становится историей.
- Технику (схема БД, топики, фреймворки) держим в тех же границах, что и в спеке: только в разделах,
  соответствующих «Технической реализации». Домен в change-документе — без техники.
- Задачи в разделе 5 — не план реализации со степенью детализации до строк, а перечень срезов и скиллов;
  подробный план строит `superpowers:writing-plans` уже по change-документу.
