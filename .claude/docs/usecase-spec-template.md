# Use Case спецификация: формат

Спецификация сервиса — контракт между бизнесом и разработкой, описывающий **один Bounded Context в доменных терминах**. Заполняется совместно бизнес-аналитиком, архитектором и разработчиками; читается человеком, используется AI-агентом как memory bank и как источник для генерации кода, диаграмм (Structurizr) и индексации (GraphRAG).

Эталонный заполненный пример формата — сервис `order-service` (контекст Order с тремя агрегатами: Order, Dispute, Refund).

## Принципы

1. **Единица спеки — Bounded Context, не агрегат.** Один контекст = одна спека. Если в контексте несколько агрегатов — спека разбивается на корневой файл (секции уровня контекста) и по файлу на агрегат (секции уровня агрегата). Дробить контекст по агрегатам на отдельные спеки нельзя: Ubiquitous Language, Context Map, роли — свойства контекста.
2. **Домен без техники.** Все секции, кроме «Технической реализации», пишутся в доменных терминах. Фреймворки, аннотации, схема БД, механизмы доставки (Outbox), топики, стек, контейнеры — **только** в разделе «Техническая реализация».
3. **Ничего не дублируется.** Каждый факт живёт в одном каноническом месте; остальные ссылаются. События описываются у агрегата-владельца; переходы — в матрице жизненного цикла; ошибки — в командах и бизнес-правилах.
4. **Карточки + строгие таблицы.** Команды, запросы, use cases — карточки `### Имя` с размеченными полями (читаемо человеку, парсится агентом/GraphRAG). Структурные секции (доступ, события, интеграции) — таблицы с нормализованным словарём.
5. **Контекст не претендует на знание соседей.** Соседние контексты — только как рёбра на стыке (Context Map). Полная Context Map и классификация субдоменов — артефакт уровня домена, не этой спеки.

## Раскладка файлов

```
docs/spec/
  <service>-spec.md          # корень: секции уровня КОНТЕКСТА
  aggregates/
    <aggregate>.md           # по файлу на агрегат: секции уровня АГРЕГАТА
```

Для одноагрегатного контекста папка `aggregates/` может отсутствовать — секции агрегата идут в корневом файле после контекст-секций. Правило «корень + подфайлы» включается с 2+ агрегатов.

**Минимальный frontmatter** (только для идентичности чанка при индексации):
- корень: `context: <service>`, `bounded-context: <BC>`;
- файл агрегата: `context: <service>`, `aggregate: <Aggregate>`.

Больше во frontmatter ничего не кладём — всё, что выводимо из путей/имён или есть в теле, не дублируем. Владелец, статус и т.п. — строкой в тексте §1.

## Секции уровня контекста (корневой файл)

Нумерация сквозная (1–11), ссылки между разделами — по имени с markdown-якорем (`[Интеграции](#2-интеграции)`).

| № | Раздел | Что внутри |
|---|---|---|
| 1 | **Bounded Context** | контекст, субдомен (Core/Supporting/Generic), владелец, миссия; таблица агрегатов со ссылками на файлы; что внутри/вне границы; стыки (типы связи) |
| 2 | **Интеграции (Context Map)** | одна mermaid-диаграмма контекст-карты + таблица рёбер (нормализованный словарь) + подраздел «Контракты» (ссылки на OpenAPI/AsyncAPI) |
| 3 | **Ubiquitous Language** | глоссарий контекста (термин — код — определение); «не путать» |
| 4 | **Роли и доступ** | роли контекста + общие ABAC-правила + PII; доступ к операциям — в §Доступ каждого агрегата |
| 5 | **Доменные события** | контракт публикуемого языка: таблица «агрегат → внешние события → топик»; полное описание событий — у агрегатов |
| 6 | **Use Cases** | сквозные сценарии карточками `### UC-N` (актор, агрегаты, основной поток, альтернативы) |
| 7 | **Процессы** | Saga / Process Manager: кросс-агрегатные процессы, sequence-диаграммы |
| 8 | **UI-спецификация** | связь статусов с UI (бейджи), тексты ошибок для пользователя |
| 9 | **Критерии приёмки** | Given / When / Then на use cases и ключевые бизнес-правила |
| 10 | **Нефункциональные требования** | таблица: производительность, доступность, согласованность, безопасность, наблюдаемость, капасити (целевые значения, без инструментов) |
| 11 | **Техническая реализация** | **единственный технический раздел**: контейнеры C2, таблица «слой → стек → реализация», подраздел «Схема БД» (ER + индексы) |

## Секции уровня агрегата (файл агрегата)

Нумерация сквозная (1–7).

| № | Раздел | Что внутри |
|---|---|---|
| 1 | **Доменная модель** | агрегат-корень + сущности (таблица), value objects (таблица «VO — инвариант»), class-диаграмма; ссылка на хранение → §Техническая реализация |
| 2 | **Жизненный цикл** | таблица статусов + матрица переходов (триггеры: команды, события, политики/таймауты) + state-диаграмма |
| 3 | **Доступ** | матрица «операция × роль» + ABAC по операциям (роли определены в корне §4) |
| 4 | **Бизнес-правила** | список `BR-<префикс>NN` с типом (инвариант/предусловие/постусловие), затрагиваемой командой и кодом ошибки |
| 5 | **Команды** | карточки `### Имя`: Переход · Вход · Предусловия · Логика · Эмитит · Ошибки |
| 6 | **Доменные события** | таблица «событие — триггер — scope (внутреннее/внешнее) — подписчики» |
| 7 | **Запросы** | карточки `### Имя`: Вопрос · Параметры · Возвращает · Логика (источник чтения, фильтр, согласованность) |

## Конвенции

- **VO** описываются через **инвариант, который они защищают** (не через поля/типы — это БД). Для sum-типов — варианты (`Discount`: `Percentage | Fixed`).
- **Бизнес-правила** — код с префиксом агрегата (`BR-O01` Order, `BR-D01` Dispute, `BR-R01` Refund), чтобы не сталкивались между агрегатами.
- **Команды vs реакции/политики.** В §Команды — только публичные команды от акторов. Реакции на события и политики (таймауты) **не выносятся отдельными карточками** — они уже есть в матрице переходов (§Жизненный цикл) и в §Доменные события.
- **Каталога ошибок нет.** Коды ошибок живут в §Команды (поле «Ошибки») и §Бизнес-правила; тексты для пользователя — в §UI; HTTP-маппинг — артефакт API (§Техническая реализация / OpenAPI).
- **Кросс-агрегатные ссылки — по ID, без FK** (`<other>_id` — логическая ссылка). Это отражается и в class-диаграммах, и в ER (§Техническая реализация).
- **Литерал `not-declared`** — для обязательного поля, данных по которому нет (явный gap-сигнал, не пустота).

### Нормализованный словарь интеграций

Под Structurizr-генерацию значения в таблице рёбер — из контролируемого словаря:
- `направление` ∈ `inbound | outbound | bidirectional`;
- `канал` ∈ `sync | async | sync+async`;
- `связь` (Context Mapping) ∈ `customer-supplier | conformist | ohs | acl | published-language | shared-kernel`.

### Контракты на рёбрах

Каждое ребро ссылается на **авторитетный контракт-файл**, а не описывает его прозой:
- REST → OpenAPI-файл; Kafka/async → AsyncAPI-файл.
- Владелец контракта определяется типом связи: для `conformist` и потребляемых событий — upstream-контекст; для своих REST и публикуемых событий (`ohs`/published-language) — этот контекст.

### Диаграммы

- **Поведенческие** (state machine в §Жизненный цикл, sequence в §Процессы) — рисуются вручную (mermaid).
- **Структурные/C4** — одна контекст-карта (mermaid) в §Интеграции; ER — в §Техническая реализация. Полные C1/C2/C3 при необходимости генерирует Structurizr из таблиц §Интеграции и §Техническая реализация.

## Tier

Глубина спеки зависит от архитектурного стиля сервиса:

- **Tier A** — слоёный сервис (Controller → Service → Repository) без `usecase-pattern`. §Доменная модель — только ER + таблицы; §Доменные события и §Процессы — пропускаются (с однострочной пометкой); агрегаты не выделяются (один «модуль»).
- **Tier B** — `usecase-pattern` (UseCase + Handler, ± CQRS-маркеры), UCP Level 1–2. Команды/запросы = UseCase-классы; §Доменные события — если события реально публикуются.
- **Tier C** — DDD / Hexagonal (агрегаты, доменные события, ports/adapters), UCP Level 3–4. Полная глубина, разбивка по агрегатам.

Tier указывается в заголовке спеки. As-is снимок существующего сервиса из кода (без бизнес-брифа) генерируется отдельным скиллом `ucp-spec-tier-0` в этот же формат, с `not-declared` там, где в коде данных нет.

Раздел, неприменимый на текущем Tier, не опускается молча — пишется заголовок + однострочная пометка («Не применимо на Tier A»).
