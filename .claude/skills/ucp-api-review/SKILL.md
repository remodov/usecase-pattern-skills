# Ревью контракта REST API

Ты ревьюишь контракт REST API (OpenAPI-спека, код контроллера, DTO или обработка ошибок) на соответствие требованиям `rest-api/*`.

## Инструкции

1. **Прочитай индекс правил** `.claude/docs/backend/rest-api/spec.md` — все коды с формулировками + сводка антипаттернов (X-коды). Это рабочий вход; цитируй в findings конкретный код. Полную версию `.claude/docs/backend/rest-api/references/java/implementation.md` (примеры, обоснование) открывай **точечно по разделу**, когда нужно уточнить нюанс правила — не читай целиком ради экономии контекста.

2. **Определи объект ревью.** Если пользователь назвал файлы — бери их. Иначе:
   - Посмотри `git diff` на недавно изменённые файлы
   - Найди OpenAPI-спеки (`*.yaml`, `*.yml` в `resources/openapi` или похоже)
   - Найди REST-контроллеры, DTO, обработчики исключений

3. **Прогон по всем требованиям домена.** Проверь каждое применимое правило (в скобках — префиксы кодов, которые цитируешь в findings):
   - Формат URL — `R-URL-*`, `R-PRIN-*`
   - Ресурсы — `R-RES-*`
   - Вложенность — `R-NEST-*`
   - HTTP-методы — `R-MTH-*`
   - Alias-сегменты — `R-ALIAS-*`
   - Action-эндпоинты — `R-ACT-*`
   - Query-параметры — `R-QRY-*`
   - JSON-поля — `R-FLD-*`
   - Формат ответа — `R-RSP-*`
   - Заголовки — `R-HDR-*`
   - Обработка ошибок — `R-ERR-*` (RFC 9457, `application/problem+json`, URN в `type`, `violations`)
   - Версионирование — `R-VER-*`
   - OpenAPI-метаданные — `R-OAS-*`
   - Rate limiting — `R-RATE-*`
   - Файлы / Deprecation / Batch / Async / Локализация — `R-FILE-*`, `R-DEP-*`, `R-BATCH-*`, `R-ASYNC-*`, `R-LOC-*`

4. **Формат finding, локализация, серьёзность, резюме, запрет правок** — см. `.claude/docs/shared/review-format/spec.md` (правила `review-format/*`). Перед каждым finding обязательна Read-проверка строки (`review-format/*`), поле `Строка` в формате обязательно (`review-format/finding-carries-line-and-rule`). В качестве `<КодПравила>` используй конкретный код из требований `rest-api/*` (`rest-api/operational-endpoints-outside-api`, `rest-api/error-type-is-stable-category`, `rest-api/methods-match-semantics` и т. п.) — не номер раздела.

   Для finding, у которого место — путь эндпоинта в OpenAPI-спеке (а не строка кода), указывай его как `<spec.yaml>:<СтрокаНомер>` после Read-проверки + цитата строки в поле `Строка`. Если finding относится к самому контракту (форма URL, метод), а конкретная строка не локализуема — это не finding, а архитектурное замечание; вынеси его в отдельный раздел отчёта.

5. **Доменные ориентиры для серьёзности** (`review-format/severity-scale-is-shared`):
   - **Критично** — ломает стандарт контракта: неправильный HTTP-метод, отсутствующий формат ошибки, неправильный статус-код.
   - **Предупреждение** — отклонение от конвенции: нейминг, отсутствие OpenAPI-метаданных.
   - **Замечание** — предложение по улучшению.
