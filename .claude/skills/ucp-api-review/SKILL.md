# Ревью контракта REST API

Ты ревьюишь контракт REST API (OpenAPI-спека, код контроллера, DTO или обработка ошибок) на соответствие командному REST API Style Guide.

## Инструкции

1. **Прочитай style guide** из `.claude/docs/rest-api-style-guide.md` в корне проекта. Это единственный источник правды для всех правил.

2. **Определи объект ревью.** Если пользователь назвал файлы — бери их. Иначе:
   - Посмотри `git diff` на недавно изменённые файлы
   - Найди OpenAPI-спеки (`*.yaml`, `*.yml` в `resources/openapi` или похоже)
   - Найди REST-контроллеры, DTO, обработчики исключений

3. **Прогон по ВСЕМ разделам** style guide. Проверь каждое применимое правило (в скобках — префиксы кодов, которые цитируешь в findings):
   - Формат URL — `R-URL-*`, `R-PRIN-*`
   - Ресурсы — `R-RES-*`
   - Вложенность — `R-NEST-*`
   - HTTP-методы — `R-MTH-*`
   - Alias-сегменты — `R-ALIAS-*`
   - Action-эндпоинты — `R-ACT-*`
   - Query-параметры — `R-QRY-*`
   - JSON-поля — `R-FLD-*`
   - Формат ответа — `R-RSP-*`
   - Заголовки — `R-HDR-*`
   - Обработка ошибок — `R-ERR-*` (RFC 9457, `application/problem+json`, URN в `type`, `violations`)
   - Версионирование — `R-VER-*`
   - OpenAPI-метаданные — `R-OAS-*`
   - Rate limiting — `R-RATE-*`
   - Файлы / Deprecation / Batch / Async / Локализация — `R-FILE-*`, `R-DEP-*`, `R-BATCH-*`, `R-ASYNC-*`, `R-LOC-*`

4. **Формат finding, локализация, серьёзность, резюме, запрет правок** — см. `.claude/docs/review-finding-format.md` (правила `RFF-1`..`RFF-16`). Перед каждым finding обязательна Read-проверка строки (`RFF-1`..`RFF-5`), поле `Строка` в формате обязательно (`RFF-7`). В качестве `<КодПравила>` используй конкретный код из REST API style guide (`R-URL-3`, `R-ERR-X2`, `R-MTH-X1` и т. п.) — не номер раздела.

   Для finding, у которого место — путь эндпоинта в OpenAPI-спеке (а не строка кода), указывай его как `<spec.yaml>:<СтрокаНомер>` после Read-проверки + цитата строки в поле `Строка`. Если finding относится к самому контракту (форма URL, метод), а конкретная строка не локализуема — это не finding, а архитектурное замечание; вынеси его в отдельный раздел отчёта.

5. **Доменные ориентиры для серьёзности** (`RFF-12`):
   - **Критично** — ломает стандарт контракта: неправильный HTTP-метод, отсутствующий формат ошибки, неправильный статус-код.
   - **Предупреждение** — отклонение от конвенции: нейминг, отсутствие OpenAPI-метаданных.
   - **Замечание** — предложение по улучшению.
