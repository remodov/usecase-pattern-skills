# Изменение спецификации — ревью (гейт)

Ты ревьюишь change-документ на **качество решения об изменении**, не на код-уровне: нет причины, влияние
недооценено, «совместимое» изменение на деле ломает смысл, миграция не соответствует классу, задачи нарезаны
слоями, спека после слияния разъедется.

Этот гейт прогоняется **дважды**: перед реализацией (полный) и перед слиянием (режим `merge`). Первый проход
ловит недодуманное изменение, второй — расхождение документа с тем, что реально сделали.

## Инструкции

1. **Прочитай формат** из `.claude/docs/shared/spec-change-template.md` — источник правды по разделам и
   классификации. Формат спеки — `.claude/docs/shared/usecase-spec-template.md`.

2. **Найди документ.** Пользователь назвал файл — ревьюй его. Иначе `Glob`: `docs/spec/changes/*.md` (без
   `archive/`). Документов нет — скажи это и предложи `ucp-spec-change`.

3. **Прочитай спеку**, на которую change ссылается: без неё нельзя проверить ни полноту «было → станет», ни
   список потребителей. Все утверждения документа сверяй с текстом спеки, а не принимай на слово.

4. **Прогони категории.** Каждое правило имеет код — цитируй его в замечании. Ссылки на разделы — по имени.

### SC-WHY (причина)

- **SC-WHY-1** Раздел «Зачем» отвечает на «почему это надо», а не пересказывает решение. «Добавить поле
  `cancelReason`» вместо причины → **Критично**: после слияния причина не сохранится нигде.
- **SC-WHY-2** Названы рассмотренные альтернативы и почему выбрана эта. Единственный вариант без обоснования →
  **Предупреждение**.
- **SC-WHY-3** Сказано, что ломается сегодня — на примере, а не в общих словах. Расплывчатое «неудобно» →
  **Замечание**.

### SC-DIFF (что меняется)

- **SC-DIFF-1** Каждая строка «Что меняется» указывает конкретный файл и раздел спеки. Строка без адреса →
  **Критично**: при слиянии её пропустят.
- **SC-DIFF-2** Все названные разделы **существуют** в спеке (сверь `Grep`). Ссылка на несуществующий раздел →
  **Критично**.
- **SC-DIFF-3** Перечислены **все** затронутые разделы, не только очевидный. Меняется команда — проверь, есть
  ли в таблице «Доменные события», матрица переходов, «Доступ», «Критерии приёмки». Пропуск связанного раздела
  → **Критично**: спека после слияния будет противоречить сама себе.
- **SC-DIFF-4** У каждой строки заполнены и «было», и «станет». Только «станет» → **Предупреждение**: нечего
  сверять при слиянии.
- **SC-DIFF-5** Домен без техники: схема БД, топики, фреймворки — только в строках, адресующих «Техническую
  реализацию». Протечка в доменную строку → **Предупреждение**.

### SC-IMP (влияние)

- **SC-IMP-1** Класс изменения объявлен: `compatible` / `breaking` / `semantic-break`. Нет класса →
  **Критично**.
- **SC-IMP-2** Класс соответствует содержанию. Удаление или переименование поля, смена типа, убранная команда,
  ужесточённое предусловие, объявленные `compatible` → **Критично**.
- **SC-IMP-3** **Смена смысла при прежнем контракте** классифицирована как `semantic-break`, а не
  `compatible`. То же поле стало значить другое, статус сменил условие перехода, изменилась единица измерения
  → **Критично**. Это опаснее `breaking`: схема и компилятор молчат, потребитель узнаёт в проде.
- **SC-IMP-4** Потребители названы поимённо — по «Интеграции (Context Map)» и подписчикам из «Доменные
  события». «Возможно, затронет другие сервисы» → **Критично**.
- **SC-IMP-5** Для `breaking` и `semantic-break` сказано, как потребитель узнает об изменении. Молчание →
  **Предупреждение**.

### SC-MIG (миграция)

- **SC-MIG-1** У `breaking` есть стратегия expand-contract: добавить новое → перевести потребителей → удалить
  старое, тремя различимыми шагами. Одномоментная замена → **Критично**.
- **SC-MIG-2** У изменения внешнего события — новая версия рядом со старой (`vN+1`), а не правка старой на
  месте. Правка на месте → **Критично**: у события есть потребители, которых нельзя обновить атомарно.
- **SC-MIG-3** Смена термина Ubiquitous Language сопровождается ADR и обновлением глоссария. Переименование
  «по ходу» → **Предупреждение**.
- **SC-MIG-4** У `compatible` раздел заполнен явным «не требуется», а не пуст. Пустой раздел →
  **Замечание**: непонятно, продумали или забыли.

### SC-TASK (задачи)

- **SC-TASK-1** Задачи нарезаны **вертикальными срезами** — каждый собирается и проверяется целиком.
  Горизонтальные слои («все DTO», «все контроллеры», «все тесты») → **Критично**: их нельзя проверить до
  последней фазы, и ошибка дизайна вскроется в конце.
- **SC-TASK-2** Каждая задача называет конкретный `ucp-*` скилл, а не прозу. «Реализовать отмену» →
  **Предупреждение**.
- **SC-TASK-3** Задачи покрывают все строки «Что меняется». Раздел спеки меняется, а задачи на него нет →
  **Предупреждение**.
- **SC-TASK-4** Изменение схемы БД имеет отдельную задачу с `ucp-pg-migration-design` и парным review — для
  DDL ревью обязателен. Миграция внутри общей задачи → **Предупреждение**.

### SC-ACR (критерии приёмки)

- **SC-ACR-1** Приёмка в формате Given / When / Then. Свободная проза → **Предупреждение**.
- **SC-ACR-2** Покрыто и новое поведение, и путь ошибки. Только успешный путь → **Предупреждение**.
- **SC-ACR-3** Критерии в доменных терминах, а не через HTTP-коды и имена эндпоинтов: они переезжают в спеку.
  Приёмка через API → **Предупреждение**.
- **SC-ACR-4** Каждое новое или изменённое бизнес-правило покрыто хотя бы одним сценарием. Непокрытое →
  **Предупреждение**.

### SC-SCOPE (границы документа)

- **SC-SCOPE-1** Один документ — одно изменение. Два несвязанных → **Критично**: при слиянии они разъедутся.
- **SC-SCOPE-2** Frontmatter несёт `context`, `change`, `status`, `level`. Отсутствие `status` →
  **Предупреждение**, остального → **Замечание**.
- **SC-SCOPE-3** Изменение вообще требует документа: опечатка, переформулировка без смены смысла, заполнение
  пропущенного раздела → **Замечание** «правится в спеке напрямую».
- **SC-SCOPE-4** Документ лежит в `docs/spec/changes/`, имя `<YYYY-MM-DD>-<slug>.md`. Иначе → **Замечание**.

### SC-MRG (готовность к слиянию — режим `merge`)

- **SC-MRG-1** Все строки «Что меняется» отражены в спеке. Не перенесённая в спеку строка → **Критично**.
- **SC-MRG-2** Критерии приёмки переехали в «Критерии приёмки» спеки. Нет → **Критично**.
- **SC-MRG-3** Новые термины попали в «Ubiquitous Language». Нет → **Предупреждение**.
- **SC-MRG-4** Документ описывает то, что реально сделано. Расхождение с кодом → **Критично**: спека
  зафиксирует несуществующее поведение.
- **SC-MRG-5** `status: merged`, дата проставлена, файл уходит в `changes/archive/`. Нет → **Предупреждение**.

## Формат вывода

5. **Замечания**:

   ```
   <Файл>:<Раздел>  [<КодПравила>]  <Серьёзность>
     Проблема: <однострочно>
     Почему: <какое свойство изменения нарушено>
     Как исправить: <что добавить / переклассифицировать / переписать>
   ```

   Примеры `<Раздел>`: `Влияние`, `Что меняется · строка 3`, `Задачи · срез 2`.

   Серьёзности: **Критично** (изменение сломает потребителей или спека разъедется — чинить до реализации) ·
   **Предупреждение** (слабость решения, дорогая переделка) · **Замечание** (придирка).

6. **Резюме**:

   ```
   Изменение: <change> · класс: <compatible|breaking|semantic-break> · статус: <status>
   Замечаний: Критично <n> · Предупреждение <n> · Замечание <n>
   Топ-категорий: <топ-3>
   Вердикт: <готово к реализации | готово к слиянию | требует переработки | недостаточно материала>
   ```

   - `готово к реализации` — 0 Критично, ≤ 5 Предупреждений (полный режим).
   - `готово к слиянию` — 0 Критично по SC-MRG (режим `merge`).
   - `требует переработки` — есть Критично ИЛИ > 5 Предупреждений.
   - `недостаточно материала` — не заполнены «Зачем», «Что меняется» или «Влияние».

7. **Ничего не модифицируй** — ни change-документ, ни спеку. Только сообщай; `Как исправить` — текстом.

8. **Если findings нет** — скажи явно и перечисли, какие категории покрыл. Молчаливое «всё хорошо» — плохой
   отчёт.

## Режимы

- **По умолчанию** — SC-WHY, SC-DIFF, SC-IMP, SC-MIG, SC-TASK, SC-ACR, SC-SCOPE (перед реализацией).
- **merge** (`merge`) — SC-MRG плюс SC-DIFF (перед слиянием и архивированием).
- **Fast** (`fast`) — только кандидаты на Критично: SC-WHY-1, SC-DIFF-1, SC-DIFF-2, SC-DIFF-3, SC-IMP-1,
  SC-IMP-2, SC-IMP-3, SC-IMP-4, SC-MIG-1, SC-MIG-2, SC-TASK-1, SC-SCOPE-1.

## Парность

Цикл: `ucp-spec-change` (propose) → **этот скилл** → правки → design-скиллы по «Задачам» → реализация →
**этот скилл** (`merge`) → `ucp-spec-change` (merge) → архив.
