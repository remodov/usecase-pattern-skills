# Use Case спецификация — проектирование

Ты пишешь Use Case спецификацию одного **Bounded Context** в доменных терминах. Формат описан в `.claude/docs/usecase-spec-template.md` — **прочитай его первым делом и следуй ему как обязательному**.

## Зависимости

- Плагин `superpowers` — планирование, TodoWrite (если нет — работаешь без хелперов).
- MCP `context7` (`mcp__plugin_context7_context7__*`) — актуальная документация по библиотекам (если не подключён — ссылки не проверяешь).

Если зависимостей нет — сообщи в начале ответа, не падай молча.

## Инструкции

1. **Прочитай формат** из `.claude/docs/usecase-spec-template.md`. Не выдумывай свои секции, имена и порядок.

2. **Определи уровень зрелости** (глубина секций; одна ось):
   - **Уровень 1 — Слоёный** — Controller → Service → Repository, без `usecase-pattern`, агрегатов нет.
   - **Уровень 2 — Use Case Pattern** — `usecase-pattern` (UseCase + Handler); CQRS (`UseCaseCommand`/`UseCaseQuery` + Read Model) — опция этого уровня, не отдельный уровень.
   - **Уровень 3 — DDD + Hexagonal** — агрегаты, доменные события, ports/adapters (DDD и Hexagonal — один уровень).

   Осмотри проект на признаки (`core/` + `adapter/`, `AggregateRoot`, `Entity<ID>`, импорты `usecase-pattern`). Если непонятно — **спроси**. Этот скилл **не делает as-is из кода**: если на входе только код без бизнес-брифа — остановись и предложи `ucp-spec-tier-0`.

3. **Раскладка файлов — всегда корень + `aggregates/`:**
   - корень `docs/spec/<service>-spec.md` — секции контекста;
   - `docs/spec/aggregates/<unit>.md` — **по файлу на каждый домен-юнит**, всегда отдельным файлом (даже если он один, на любом уровне).

   Домен-юнит = агрегат на Уровне 3; на Уровне 1–2 (DDD-агрегатов нет) — центральная **сущность** контекста (`product.md`, `notification.md`). Файл всё равно в `aggregates/`. Единый формат во всех спеках.

4. **Определи вход.** Спека пишется **от бизнес-описания**, не от кода: markdown-файл в репо, вставка в промпт или внешний документ (попроси вставить текст). Если входа не хватает даже на Уровень 1 (нет глоссария, акторов, операций) — **остановись и спроси**, не выдумывай бизнес-факты.

5. **Заполни секции уровня контекста** (корневой файл; нумерация сквозная):
   1. Bounded Context · 2. Интеграции (Context Map) · 3. Ubiquitous Language · 4. Роли и доступ · 5. Доменные события (контракт) · 6. Use Cases · 7. Процессы · 8. UI · 9. Критерии приёмки (GWT) · 10. НФТ · 11. Техническая реализация.

6. **Заполни секции уровня домен-юнита** (по файлу на юнит в `aggregates/`, всегда отдельным; нумерация 1–N внутри файла):
   1. Доменная модель · 2. Жизненный цикл · 3. Доступ · 4. Бизнес-правила · 5. Команды · 6. Доменные события · 7. Запросы.

7. **Соблюдай конвенции формата:**
   - **Домен без техники.** §1–§10 — доменные термины. Вся техника (фреймворки, аннотации, схема БД/ER, Outbox, топики, стек, контейнеры C2) — только в §11 «Техническая реализация» (таблица по слоям + подраздел «Схема БД»).
   - **Команды/запросы/UC — карточки** `### Имя` с размеченными полями. Команда: Переход · Вход · Предусловия · Логика · Эмитит · Ошибки. Запрос: Вопрос · Параметры · Возвращает · Логика.
   - **Реакции/политики НЕ выносим** отдельными карточками — они в матрице переходов (§Жизненный цикл) и §Доменные события.
   - **События владеются агрегатами** (полное описание в §Доменные события агрегата); в корне — тонкий контракт «агрегат → внешние события → топик».
   - **Каталога ошибок нет.** Коды — в §Команды (поле «Ошибки») и §Бизнес-правила; тексты UI — в §UI; HTTP-маппинг — §Техническая реализация / OpenAPI.
   - **Доступ** — матрица «операция × роль» в §Доступ агрегата; роли + общие ABAC-правила — в корне §4. Поля `Актор` в карточках команд нет (доступ только в матрице).
   - **VO** — через инвариант (не поля/типы). **BR** — с префиксом агрегата (`BR-O01`, `BR-D01`, `BR-R01`).
   - **Кросс-агрегатные/кросс-контекстные ссылки — по ID, без FK.**
   - **Минимальный frontmatter**: корень `context` + `bounded-context` + `level`; файл юнита `context` + `aggregate` + `level`. Больше ничего.
   - **Интеграции** — нормализованный словарь (`inbound|outbound|bidirectional`, `sync|async|sync+async`, `customer-supplier|conformist|ohs`). Контракты на рёбрах — ссылки на OpenAPI (REST) / AsyncAPI (Kafka).
   - **Ссылки между разделами** — по имени с markdown-якорем (`[Жизненный цикл](#2-жизненный-цикл)`).
   - **Диаграммы**: state machine (§Жизненный цикл) и sequence (§Процессы) — рисуешь mermaid; одна контекст-карта (§Интеграции); ER (§Техническая реализация). Полные C1/C2/C3 не рисуешь — их генерит Structurizr.

8. **Глубина по уровню:**
   - **Уровень 1**: §Доменная модель = ER + список таблиц (без агрегатов/VO); §Команды = операции/endpoint'ы; §Доменные события и §Процессы — пропусти с пометкой; §Жизненный цикл — только если есть статусы.
   - **Уровень 2**: §Команды = `UseCase`/`UseCaseCommand`; §Доменные события — если события реально публикуются; Read Model — при CQRS-опции.
   - **Уровень 3**: полная глубина, разбивка по агрегатам.

   Неприменимый раздел **не опускай молча** — заголовок + однострочная пометка («Не применимо на Уровне 1»). Нет данных для обязательного поля — литерал `not-declared`.

9. **Код не пиши.** Скилл производит только markdown-спеку. Код генерируют `ucp-ddd-tactical-design`, `ucp-pattern-design`; OpenAPI — `ucp-api-design`.

10. **Самопроверка перед выдачей:**
    - Уровень и число агрегатов соответствуют проекту; раскладка файлов корректна.
    - Каждая команда/запрос/UC — карточка с полями; в §Команды нет реакций/политик.
    - Каждое событие в командах/реакциях есть в §Доменные события агрегата; внешние — в корневом контракте.
    - Каждый код ошибки из §Команды осмыслен; каждый BR имеет код с префиксом агрегата.
    - В §1–§10 нет техники (аннотаций, DDL, фреймворков); вся техника — в §11.
    - frontmatter минимален; ссылки — якорные; неприменимые разделы помечены.

11. **Структура вывода:**
    1. Резюме: уровень зрелости, имя контекста, домен-юниты (файлы в `aggregates/`), какие разделы намеренно минимальны.
    2. Дерево созданных файлов в `docs/spec/` — точные пути.
    3. Заметки: какие downstream-скиллы возьмут спеку дальше (`ucp-ddd-tactical-design`, `ucp-pattern-design`, `ucp-api-design`).
