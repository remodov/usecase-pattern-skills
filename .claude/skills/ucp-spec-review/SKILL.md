# Use Case спецификация — ревью (design-критик)

Ты ревьюишь Use Case спецификацию (или черновик Event Storming) на **качество дизайна**, не на код-уровне: противоречия в доменном языке, агрегаты с лишними инвариантами, команды без владельца/обработки ошибок, события без потребителей, неясный владелец данных, забытые зоны отказа, критерии приёмки, не покрывающие правила, протечки техники в доменные разделы. Плюс **читаемость подачи** (`SR-RD`): спека, которую человек не может прочесть, не выполняет свою половину работы, даже если машина её разбирает.

Это **AI как design-критик**, парный к `ucp-spec-design`: ищем трещины до того, как против спеки начнут писать код.

## Инструкции

1. **Прочитай формат** из `.claude/docs/shared/spec-format/spec.md` — он источник правды по структуре (корень = контекст-секции + по файлу на домен-юнит в `aggregates/`, всегда отдельным), уровню зрелости и конвенциям. При проверке схемы БД (раздел «Техническая реализация» → «Схема БД») применяй `backend/pg-types/spec.md` (`PG-T-NNN`): антипаттерны (`varchar(255)`, `timestamp` без TZ, `varchar(36)` для UUID, `float` для денег) — критичные находки. Правила подачи — требования `spec-format/*` в том же файле (лид, источники вне текста, собранные пробелы, перечни таблицами, вводная фраза, язык); на них опирается категория `SR-RD`. Скелеты разделов — `references/service-spec.md` и `references/aggregate-spec.md`.

2. **Найди спеку.** Если пользователь назвал файлы — ревьюй их. Иначе `Glob`: `docs/spec/*-spec.md` (корень) + `docs/spec/aggregates/*.md`. Возможны: сгенерированная спека, спека от руки в одном файле, черновик Event Storming.

3. **Определи уровень зрелости и раскладку.** Уровень (0/1/2/3) — из frontmatter `level` или содержания: маркер `(as-is)` / `level: 0` → Уровень 0 (реверс из кода, глубину не критикуем — это снимок); агрегаты+события+порты → 3; UseCase-Handler → 2; только Controller/Service → 1. Раскладка всегда: корень + `aggregates/<unit>.md`. Укажи в начале отчёта.

4. **Прогони категории.** У каждого правила код (`SR-UL-1` и т.п.) — цитируй в замечании. Неприменимую на уровне категорию помечай явно («неприменимо на Уровне 1»). Ссылки на разделы — по **имени** (не §N).

### SR-LV (Maturity level consistency)

- **SR-LV-1** Объявленный уровень совпадает с глубиной. *Уровень 3* без агрегатов/событий → **Критично**. *Уровень 1* с полными агрегатами → **Предупреждение**. *Уровень 0* (as-is) — глубину не критикуем (снимок кода), но `not-declared` в обязательных полях допустим и ожидаем.
- **SR-LV-2** Разделы, обязательные для уровня, присутствуют; неприменимые — с явной пометкой, а не молча опущены. Молчаливое опущение обязательного → **Критично**.
- **SR-LV-3** Домен-юнит вынесен в отдельный файл `aggregates/<name>.md` (всегда, даже один). Юнит-секции (модель/цикл/правила/команды/запросы) в корневом файле → **Предупреждение**. Frontmatter несёт `level` (корень и юниты) → отсутствие → **Замечание**.

### SR-FMT (чистота формата)

- **SR-FMT-1** **Домен без техники.** В доменных разделах (всё кроме «Технической реализации») нет фреймворков, аннотаций (`@Transactional`, `@Scheduled`), DDL/типов колонок, механизмов (Outbox, Debezium), топиков. Протечка техники → **Предупреждение** (перенести в «Техническую реализацию»).
- **SR-FMT-2** **Каталога ошибок нет** отдельным разделом. Коды ошибок — в поле «Ошибки» команд и в «Бизнес-правилах»; тексты для пользователя — в «UI». Отдельная секция «Каталог ошибок» → **Предупреждение** (старый формат).
- **SR-FMT-3** **События владеются агрегатами**: полное описание — в «Доменные события» агрегата; в корне — тонкий контракт «агрегат → внешние события → топик». Полный каталог событий в корне с дублированием → **Предупреждение**.
- **SR-FMT-4** **Реакции/политики не вынесены** отдельными карточками в «Команды» — они в матрице переходов и «Доменных событиях». Карточки-реакции → **Замечание**.
- **SR-FMT-5** **Контракты привязаны к рёбрам** «Интеграций» ссылками (OpenAPI для REST, AsyncAPI для async), а не описаны прозой. Отсутствие ссылки на контракт у внешнего ребра → **Замечание**.

### SR-RD (Читаемость подачи)

Категория проверяет, читается ли спека человеком, который сервис ещё не знает. Она **не спорит** с машиночитаемостью: реестры §11, стабильные заголовки колонок и `spec-format/lists-are-tables` остаются в силе — `SR-RD` смотрит на то, что вокруг них.

- **SR-RD-1** (`spec-format/document-opens-with-lead`, `-LEAD-2`) **Лид на месте.** Корневой файл открывается разделом `## О сервисе` (5–10 строк прозой: чем занимается · 2–3 потока · 2–3 риска) **до** §1; файл домен-юнита — `## О юните` на 2–3 строки. Документ, начинающийся сразу с «§1 Bounded Context», → **Предупреждение**. Лид есть, но это таблица, перечень разделов, цитата README или текст с кодами правил и evidence → **Замечание** (`spec-format/document-opens-with-lead`).
- **SR-RD-2** (`spec-format/evidence-outside-the-sentence`) **Evidence не в прозе.** Ссылки вида `Файл.kt:142`, `(reconstructed-from: …)` внутри предложений → **Предупреждение**: перенести в колонку `Evidence`, в блок `**Источники раздела:** …` или в сноску. Имя класса/файла **без номера строки** в прозе — допустимо, не находка. Колонка `Evidence`, переименованная в «Источник» или переставленная в реестрах §11, → **Критично** (ломает `spec-format/lists-are-tables`).
- **SR-RD-3** (`spec-format/gaps-collected-at-the-end`, `-ND-2`) **Пробелы собраны.** В конце документа есть ненумерованный `## Что не определено` с вводной фразой и таблицей `| Раздел | Чего нет | Чем закрыть |` (или пометкой «пробелов нет»). Раздела нет, а `not-declared` рассыпан по прозе разделов → **Предупреждение** (`spec-format/gaps-collected-at-the-end`). Обратная ошибка тоже находка: литерал **убран из ячейки таблицы или поля карточки**, из-за чего утверждение читается неверно (пропала строка реестра, поле «Идемпотентность» просто отсутствует), → **Критично**.
- **SR-RD-4** (`spec-format/table-fits-six-columns`) **Таблицы ≤ 6 колонок.** Таблица на 7+ колонок → **Предупреждение**: разбить на две связанные по общему ключу («что это» + «как настроено»), ключ дословно одинаков в первой колонке обеих. Обязательные реестры §11 (6 и 5 колонок) — в норме; **расширение** реестра седьмой колонкой → **Критично**.
- **SR-RD-5** (`spec-format/section-opens-with-prose`) **Прогрессивное раскрытие.** Каждый раздел и подраздел начинается с 1–3 предложений прозой, и только потом идут таблицы, карточки и диаграммы. Голая таблица (или mermaid) сразу под заголовком → **Предупреждение**. Вводная фраза, пересказывающая строки таблицы вместо объяснения её назначения, → **Замечание** (возврат к `spec-format/lists-are-tables`).
- **SR-RD-6** (`spec-format/language-is-plain`) **Язык.** Короткие предложения, активный залог, конкретное подлежащее, термины из «Ubiquitous Language». Канцелярит, отглагольные существительные («производится осуществление обработки»), безличный пассив, предложения на пять строк, транслит вместо термина → **Замечание** (систематически по всему документу → **Предупреждение**).

**Агрегация находок `SR-RD`.** Одна находка на правило на файл, а не на каждое вхождение: в замечании — счётчик и 2–3 примера («`SR-RD-2`: 41 ссылка внутри предложений, напр. §2, §5, §11»). Иначе категория забивает отчёт и топит доменные находки. Считать их отдельной строкой в резюме.

### SR-UL (Ubiquitous Language)

- **SR-UL-1** Каждый термин глоссария используется хотя бы в одном другом разделе.
- **SR-UL-2** Один концепт — ровно одно имя. Синонимы вне глоссария → **Критично**.
- **SR-UL-3** Имена use-case'ов, команд, событий используют термины глоссария.
- **SR-UL-4** У каждого термина есть определение. Голая запись → **Предупреждение**.

### SR-BC (Bounded Context)

- **SR-BC-1** В «Bounded Context» явно описаны границы (внутри / вне). Нет «вне границы» → **Предупреждение**.
- **SR-BC-2** Каждая команда принадлежит этому контексту. Чужая команда → **Критично**.
- **SR-BC-3** Нет невидимого пересечения с соседями (если «Интеграции» называют Catalog upstream-ом — спека не владеет товарами).
- **SR-BC-4** Уровень 2–3: названы соседние контексты и типы связи (нормализованный словарь `customer-supplier|conformist|ohs|…`).

### SR-AG (Aggregates / Domain Model — Уровень 3, частично 2)

- **SR-AG-1** У каждого агрегата ≤ 7 инвариантов (бизнес-правил). Больше → **Предупреждение** (кандидат на разделение).
- **SR-AG-2** Корень агрегата явный; под-сущности доступны только через него.
- **SR-AG-3** Между агрегатами ссылки **по ID, без FK и без циклов**. Композиция чужого агрегата или цикл `A.id↔B.id` → **Критично**.
- **SR-AG-4** Value Objects описаны через инвариант, иммутабельны. Мутабельный VO → **Предупреждение**.
- **SR-AG-5** У агрегата типизированный идентификатор (`OrderId`, не `Long`). Примитив → **Предупреждение**.
- **SR-AG-6** Уровень 3: каждая команда, меняющая состояние, регистрирует доменное событие (сверь «Команды» ↔ «Доменные события»). Молчаливое изменение → **Предупреждение**.

### SR-AR (Actors / Roles)

- **SR-AR-1** Каждый актор из «Use Cases»/«Команд» есть в «Роли и доступ». Осиротевший актор → **Критично**.
- **SR-AR-2** Доступ задан матрицей «операция × роль» (в «Доступ» агрегата); роли + ABAC — в корне. Отсутствие матрицы → **Предупреждение**.
- **SR-AR-3** У каждой операции в матрице доступа определены роли и (где нужно) ABAC-условие.

### SR-CM (Commands)

- **SR-CM-1** У каждой команды: тип результата, набор бизнес-ошибок (поле «Ошибки»), предусловия. Отсутствие любого → **Предупреждение**.
- **SR-CM-2** Уровень 3: каждая команда привязана к агрегату (через файл агрегата). Команда без привязки → **Критично**.
- **SR-CM-3** CQRS (Уровень 2+): команды возвращают идентификатор/пустой результат, не толстый read-DTO. Read-DTO в команде → **Предупреждение**.
- **SR-CM-4** Явный контракт идемпотентности. Money-команда без идемпотентности → **Критично**.

### SR-EV (Domain Events — Уровень 2 с Kafka, Уровень 3 всегда)

- **SR-EV-1** У каждого события минимум один потребитель (внутренний или внешний из «Интеграций»). Осиротевшее → **Критично**.
- **SR-EV-2** Имена — глаголы в прошедшем времени (`OrderPaid`, не `PayOrder`).
- **SR-EV-3** Внешнее событие с потреблением требует идемпотентного приёма. Нет пометки → **Предупреждение**.
- **SR-EV-4** Scope (внутреннее/внешнее) и подписчики указаны. Нет → **Предупреждение**.
- **SR-EV-5** Уровень 3: события публикуются транзакционно (Outbox — в «Технической реализации»). Публикация после `save()` без атомарности → **Критично**.

### SR-FD (Failure Domains)

- **SR-FD-1** У каждой внешней зависимости в «Интеграциях» — стратегия при отказе (деградация / очередь / запасной путь / отказ). Нет → **Предупреждение**.
- **SR-FD-2** «НФТ» говорит, где eventual, где strong consistency. Молчание → **Предупреждение**.
- **SR-FD-3** У внешнего вызова — таймаут или Circuit Breaker. Нет обоих → **Критично**.

### SR-DO (Data Ownership)

- **SR-DO-1** Каждая сущность имеет ровно одного владельца. Совладение → **Критично**.
- **SR-DO-2** Чтение чужих данных — через документированную интеграцию. Прямой доступ к чужим таблицам → **Критично**.
- **SR-DO-3** PII / регулируемые поля имеют политику хранения и удаления («НФТ» / Security). Нет для PII → **Критично**.

### SR-ACR (Acceptance Criteria)

- **SR-ACR-1** Каждое бизнес-правило покрыто хотя бы одним сценарием приёмки. Непокрытое → **Предупреждение**.
- **SR-ACR-2** У каждой команды есть приёмка на успех и на ошибку. Нет пути ошибки → **Предупреждение**.
- **SR-ACR-3** Приёмка в формате `Given / When / Then`. Свободная проза → **Предупреждение**.

### SR-NFR (Non-Functional)

- **SR-NFR-1** У каждого НФТ измеримый порог (`p95 ≤ 200 ms`), не общие слова. Расплывчатый → **Предупреждение**.
- **SR-NFR-2** У каждого НФТ способ измерения / алёртинга. Нет → **Предупреждение**.

## Формат вывода

5. **Замечания**:

   ```
   <Файл>:<Раздел>  [<КодПравила>]  <Серьёзность>
     Проблема: <однострочно>
     Почему: <какое свойство дизайна нарушено>
     Как исправить: <что добавить / перенести / убрать>
   ```

   Примеры `<Раздел>`: `Команды · CancelOrder`, `Доменная модель · Order`, `Интеграции · Catalog`.

   Серьёзности: **Критично** (приведёт к неправильному/небезопасному коду — чинить до кодогена) · **Предупреждение** (слабость дизайна, переписывание/скрытая связность) · **Замечание** (придирка).

6. **Резюме**:

   ```
   Уровень: <0|1|2|3> (frontmatter / выведенный) · раскладка: корень + aggregates/
   Замечаний: Критично <n> · Предупреждение <n> · Замечание <n>
   Читаемость (SR-RD): <n> из 6 правил нарушено · <читаема | требует редактуры>
   Топ-категорий: <топ-3>
   Вердикт: <готова к кодогенерации | требует переработки | недостаточно материала>
   ```

   - `готова` — 0 Критично, ≤ 5 Предупреждений **среди доменных категорий**.
   - `требует переработки` — есть Критично ИЛИ > 5 Предупреждений среди доменных категорий.
   - `недостаточно материала` — заполнено слишком мало обязательных разделов.

   `SR-RD` в вердикт о готовности к кодогенерации **не входит** (кроме своих Критично: сломанные заголовки реестров, потерянные строки, расширенные реестры) — нечитаемая спека кодогену не мешает, но мешает людям, поэтому идёт отдельной строкой «Читаемость» и чинится редактурой через `ucp-spec-design` / `ucp-spec-tier-0`.

7. **Спеку не модифицируй.** Только сообщай; `Как исправить` — текстом.

## Режимы

- **По умолчанию** — все категории.
- **Fast** (`fast`) — только кандидаты на Критично: SR-LV-1, SR-UL-2, SR-BC-2, SR-AG-3, SR-AR-1, SR-CM-2, SR-CM-4, SR-EV-1, SR-EV-5, SR-FD-3, SR-DO-1, SR-DO-2, SR-DO-3.
- **ES-черновик** (`es`) — ревью Event Storming: фокус SR-UL, SR-BC, SR-AR, SR-EV.
- **Читаемость** (`read`) — только `SR-RD`: редакторский проход по готовой спеке (лид, evidence, собранные пробелы, ширина таблиц, вводные фразы, язык). Полезен после `ucp-spec-tier-0` на большом корпусе.

## Парность

Цикл: `ucp-spec-design` → спека → `ucp-spec-review` → замечания → правки → `ucp-spec-review` (Fast) → 0 Критично → `ucp-pattern-design` / `ucp-ddd-tactical-design` / `ucp-api-design`. AI кросс-ссылается все разделы в одном проходе — ловит то, что человек при чтении сверху вниз пропускает.
