# Use Case спецификация — ревью (design-критик)

Ты ревьюишь Use Case спецификацию (или черновик Event Storming) на **качество дизайна**, не на код-уровне: противоречия в доменном языке, агрегаты с лишними инвариантами, команды без владельца/обработки ошибок, события без потребителей, неясный владелец данных, забытые зоны отказа, критерии приёмки, не покрывающие правила, протечки техники в доменные разделы.

Это **AI как design-критик**, парный к `ucp-spec-design`: ищем трещины до того, как против спеки начнут писать код.

## Инструкции

1. **Прочитай формат** из `.claude/docs/usecase-spec-template.md` — он источник правды по структуре (секции контекста + секции агрегата, раскладка «один файл / корень + `aggregates/`»), Tier и конвенциям. При проверке схемы БД (раздел «Техническая реализация» → «Схема БД») применяй `pg-types-style-guide.md` (`PG-T-NNN`): антипаттерны (`varchar(255)`, `timestamp` без TZ, `varchar(36)` для UUID, `float` для денег) — критичные находки.

2. **Найди спеку.** Если пользователь назвал файлы — ревьюй их. Иначе `Glob`: `docs/spec/*-spec.md` (корень) + `docs/spec/aggregates/*.md`. Возможны: сгенерированная спека, спека от руки в одном файле, черновик Event Storming.

3. **Определи Tier и раскладку.** Tier (A/B/C) — из заголовка или содержания (агрегаты+события → C; UseCase-Handler → B; только Controller/Service → A). Раскладка: один файл (0–1 агрегат) или корень + `aggregates/` (2+). Укажи в начале отчёта.

4. **Прогони категории.** У каждого правила код (`SR-UL-1` и т.п.) — цитируй в замечании. Неприменимую на Tier категорию помечай явно («неприменимо на Tier A»). Ссылки на разделы — по **имени** (не §N).

### SR-T (Tier consistency)

- **SR-T-1** Объявленный Tier совпадает с глубиной. *Tier C* без агрегатов/событий → **Критично**. *Tier A* с полными агрегатами → **Предупреждение**.
- **SR-T-2** Разделы, обязательные для Tier, присутствуют; неприменимые — с явной пометкой, а не молча опущены. Молчаливое опущение обязательного → **Критично**.
- **SR-T-3** Раскладка соответствует числу агрегатов (2+ агрегата в одном файле без `aggregates/` → **Предупреждение**; один агрегат, размазанный по `aggregates/` без нужды → **Замечание**).

### SR-FMT (чистота формата)

- **SR-FMT-1** **Домен без техники.** В доменных разделах (всё кроме «Технической реализации») нет фреймворков, аннотаций (`@Transactional`, `@Scheduled`), DDL/типов колонок, механизмов (Outbox, Debezium), топиков. Протечка техники → **Предупреждение** (перенести в «Техническую реализацию»).
- **SR-FMT-2** **Каталога ошибок нет** отдельным разделом. Коды ошибок — в поле «Ошибки» команд и в «Бизнес-правилах»; тексты для пользователя — в «UI». Отдельная секция «Каталог ошибок» → **Предупреждение** (старый формат).
- **SR-FMT-3** **События владеются агрегатами**: полное описание — в «Доменные события» агрегата; в корне — тонкий контракт «агрегат → внешние события → топик». Полный каталог событий в корне с дублированием → **Предупреждение**.
- **SR-FMT-4** **Реакции/политики не вынесены** отдельными карточками в «Команды» — они в матрице переходов и «Доменных событиях». Карточки-реакции → **Замечание**.
- **SR-FMT-5** **Контракты привязаны к рёбрам** «Интеграций» ссылками (OpenAPI для REST, AsyncAPI для async), а не описаны прозой. Отсутствие ссылки на контракт у внешнего ребра → **Замечание**.

### SR-UL (Ubiquitous Language)

- **SR-UL-1** Каждый термин глоссария используется хотя бы в одном другом разделе.
- **SR-UL-2** Один концепт — ровно одно имя. Синонимы вне глоссария → **Критично**.
- **SR-UL-3** Имена use-case'ов, команд, событий используют термины глоссария.
- **SR-UL-4** У каждого термина есть определение. Голая запись → **Предупреждение**.

### SR-BC (Bounded Context)

- **SR-BC-1** В «Bounded Context» явно описаны границы (внутри / вне). Нет «вне границы» → **Предупреждение**.
- **SR-BC-2** Каждая команда принадлежит этому контексту. Чужая команда → **Критично**.
- **SR-BC-3** Нет невидимого пересечения с соседями (если «Интеграции» называют Catalog upstream-ом — спека не владеет товарами).
- **SR-BC-4** Tier B/C: названы соседние контексты и типы связи (нормализованный словарь `customer-supplier|conformist|ohs|…`).

### SR-AG (Aggregates / Domain Model — Tier C, частично B)

- **SR-AG-1** У каждого агрегата ≤ 7 инвариантов (бизнес-правил). Больше → **Предупреждение** (кандидат на разделение).
- **SR-AG-2** Корень агрегата явный; под-сущности доступны только через него.
- **SR-AG-3** Между агрегатами ссылки **по ID, без FK и без циклов**. Композиция чужого агрегата или цикл `A.id↔B.id` → **Критично**.
- **SR-AG-4** Value Objects описаны через инвариант, иммутабельны. Мутабельный VO → **Предупреждение**.
- **SR-AG-5** У агрегата типизированный идентификатор (`OrderId`, не `Long`). Примитив → **Предупреждение**.
- **SR-AG-6** Tier C: каждая команда, меняющая состояние, регистрирует доменное событие (сверь «Команды» ↔ «Доменные события»). Молчаливое изменение → **Предупреждение**.

### SR-AR (Actors / Roles)

- **SR-AR-1** Каждый актор из «Use Cases»/«Команд» есть в «Роли и доступ». Осиротевший актор → **Критично**.
- **SR-AR-2** Доступ задан матрицей «операция × роль» (в «Доступ» агрегата); роли + ABAC — в корне. Отсутствие матрицы → **Предупреждение**.
- **SR-AR-3** У каждой операции в матрице доступа определены роли и (где нужно) ABAC-условие.

### SR-CM (Commands)

- **SR-CM-1** У каждой команды: тип результата, набор бизнес-ошибок (поле «Ошибки»), предусловия. Отсутствие любого → **Предупреждение**.
- **SR-CM-2** Tier C: каждая команда привязана к агрегату (через файл агрегата). Команда без привязки → **Критично**.
- **SR-CM-3** CQRS (Tier B+): команды возвращают идентификатор/пустой результат, не толстый read-DTO. Read-DTO в команде → **Предупреждение**.
- **SR-CM-4** Явный контракт идемпотентности. Money-команда без идемпотентности → **Критично**.

### SR-EV (Domain Events — Tier B с Kafka, Tier C всегда)

- **SR-EV-1** У каждого события минимум один потребитель (внутренний или внешний из «Интеграций»). Осиротевшее → **Критично**.
- **SR-EV-2** Имена — глаголы в прошедшем времени (`OrderPaid`, не `PayOrder`).
- **SR-EV-3** Внешнее событие с потреблением требует идемпотентного приёма. Нет пометки → **Предупреждение**.
- **SR-EV-4** Scope (внутреннее/внешнее) и подписчики указаны. Нет → **Предупреждение**.
- **SR-EV-5** Tier C: события публикуются транзакционно (Outbox — в «Технической реализации»). Публикация после `save()` без атомарности → **Критично**.

### SR-FD (Failure Domains)

- **SR-FD-1** У каждой внешней зависимости в «Интеграциях» — стратегия при отказе (деградация / очередь / запасной путь / отказ). Нет → **Предупреждение**.
- **SR-FD-2** «НФТ» говорит, где eventual, где strong consistency. Молчание → **Предупреждение**.
- **SR-FD-3** У внешнего вызова — таймаут или Circuit Breaker. Нет обоих → **Критично**.

### SR-DO (Data Ownership)

- **SR-DO-1** Каждая сущность имеет ровно одного владельца. Совладение → **Критично**.
- **SR-DO-2** Чтение чужих данных — через документированную интеграцию. Прямой доступ к чужим таблицам → **Критично**.
- **SR-DO-3** PII / регулируемые поля имеют политику хранения и удаления («НФТ» / Security). Нет для PII → **Критично**.

### SR-ACR (Acceptance Criteria)

- **SR-ACR-1** Каждое бизнес-правило покрыто хотя бы одним сценарием приёмки. Непокрытое → **Предупреждение**.
- **SR-ACR-2** У каждой команды есть приёмка на успех и на ошибку. Нет пути ошибки → **Предупреждение**.
- **SR-ACR-3** Приёмка в формате `Given / When / Then`. Свободная проза → **Предупреждение**.

### SR-NFR (Non-Functional)

- **SR-NFR-1** У каждого НФТ измеримый порог (`p95 ≤ 200 ms`), не общие слова. Расплывчатый → **Предупреждение**.
- **SR-NFR-2** У каждого НФТ способ измерения / алёртинга. Нет → **Предупреждение**.

## Формат вывода

5. **Замечания**:

   ```
   <Файл>:<Раздел>  [<КодПравила>]  <Серьёзность>
     Проблема: <однострочно>
     Почему: <какое свойство дизайна нарушено>
     Как исправить: <что добавить / перенести / убрать>
   ```

   Примеры `<Раздел>`: `Команды · CancelOrder`, `Доменная модель · Order`, `Интеграции · Catalog`.

   Серьёзности: **Критично** (приведёт к неправильному/небезопасному коду — чинить до кодогена) · **Предупреждение** (слабость дизайна, переписывание/скрытая связность) · **Замечание** (придирка).

6. **Резюме**:

   ```
   Tier: <A|B|C> (объявленный / выведенный) · раскладка: <один файл | корень + aggregates>
   Замечаний: Критично <n> · Предупреждение <n> · Замечание <n>
   Топ-категорий: <топ-3>
   Вердикт: <готова к кодогенерации | требует переработки | недостаточно материала>
   ```

   - `готова` — 0 Критично, ≤ 5 Предупреждений.
   - `требует переработки` — есть Критично ИЛИ > 5 Предупреждений.
   - `недостаточно материала` — заполнено слишком мало обязательных разделов.

7. **Спеку не модифицируй.** Только сообщай; `Как исправить` — текстом.

## Режимы

- **По умолчанию** — все категории.
- **Fast** (`fast`) — только кандидаты на Критично: SR-T-1, SR-UL-2, SR-BC-2, SR-AG-3, SR-AR-1, SR-CM-2, SR-CM-4, SR-EV-1, SR-EV-5, SR-FD-3, SR-DO-1, SR-DO-2, SR-DO-3.
- **ES-черновик** (`es`) — ревью Event Storming: фокус SR-UL, SR-BC, SR-AR, SR-EV.

## Парность

Цикл: `ucp-spec-design` → спека → `ucp-spec-review` → замечания → правки → `ucp-spec-review` (Fast) → 0 Критично → `ucp-pattern-design` / `ucp-ddd-tactical-design` / `ucp-api-design`. AI кросс-ссылается все разделы в одном проходе — ловит то, что человек при чтении сверху вниз пропускает.
