**Дата:** 2026-05-08

**Файл:** `.claude/docs/rest-api-style-guide.md` (1765 строк, 21 раздел)

## 1. Цель

Привести гайд к единому формату правил с кодами (как `usecase-pattern-style-guide.md`), чтобы скилл `ucp-api-review` цитировал коды (`R-URL-3`) в findings вместо номеров секций («см. раздел 5.3»). Параллельно — ревизия 6 спорных мест.

В github-репо файл отсутствует. Будет добавлен впервые.

## 2. Формат правил

- Подгруппа по аспекту, префикс `R-XXX-` (3–5 букв)
- Положительные: `R-URL-1`, `R-URL-2`…
- Запреты: `R-URL-X1`, `R-URL-X2`…
- Структура секции:
  ```
  ## N. <Аспект>
  ### N.1 Обязательно
  - **R-XXX-1.** <правило>
    <пример «правильно»>
  ### N.2 Запрещено
  - **R-XXX-X1.** <запрет>
    <пример «неправильно»>
  ```

Тот же формат, что в `usecase-pattern-style-guide.md` §3.1/§3.2.

## 4. Решения по 6 спорным местам

Пользователь делегировал решения. Применяются без дополнительных вопросов в ходе рефакторинга.

### 4.1. null в ответе vs null в PATCH

**Проблема:** `R-RSP-X*` запрещает null в успешном ответе, но в JSON Merge Patch (RFC 7396) null в теле PATCH означает «удалить поле».

**Решение:** Разнести по разным правилам с явной перекрёстной ссылкой.

- `R-RSP-X1`: «В успешном ответе (2xx) поле со значением null исключается из JSON. Если нет данных — нет поля.»
- `R-FLD-N` (новое): «В теле PATCH-запроса (RFC 7396 JSON Merge Patch) явный `null` — команда удалить поле. Это семантика запроса, не нарушение `R-RSP-X1`.»
- В обоих правилах сноска на парное.

### 4.2. `{id}` в URL vs уникальные имена в OpenAPI

**Проблема:** В дизайн-разделе URL — `/orders/{id}/items/{id}`. OpenAPI требует уникальных имён параметров.

**Решение:** Двойной стандарт явно.

- `R-NEST-3` (Обязательно): «В дизайн-документации и обсуждении пути используется `{id}` — контекст пути устраняет неоднозначность: `/orders/{id}/items/{id}`.»
- `R-OAS-N` (Обязательно): «В OpenAPI-спецификации параметры пути именуются уникально по контексту: `{orderId}`, `{itemId}`. Это требование инструмента — Swagger/Redoc не работают с одинаковыми именами параметров.»

### 4.3. page 1-based vs Spring 0-based

**Проблема:** API контракт (1-based удобнее для людей) расходится со Spring Data Pageable (0-based).

**Решение:** Контракт — 1-based. Реализация — конфигом, не кодом.

- `R-QRY-N` (Обязательно): «Параметр `page` — 1-based: `page=1` — первая страница. `page=0` запрещён.»
- В разделе bootstrap-style-guide (вне scope этого рефакторинга) фиксируется: `spring.data.web.pageable.one-indexed-parameters=true`. Здесь — только контракт.

Ручная конвертация `page-1` в коде запрещена — теряется единая точка истины.

### 4.4. Новое enum-значение и forward-compat

**Проблема:** Правило «новое enum-значение не breaking» сломает наивных клиентов (switch без default).

**Решение:** Оставить «не breaking», добавить парное обязательство клиентов.

- `R-VER-N` (Обязательно, для клиентов): «Клиент API ОБЯЗАН игнорировать (или явно обрабатывать как unknown) неизвестные значения enum и неизвестные поля в ответе. На этом обязательстве основано правило `R-VER-K`: добавление нового enum-значения / нового поля — non-breaking.»

Это формализует контракт forward-compatibility, который раньше был устным.

### 4.5. RFC 9457 `type` URI и dead-link риск

**Проблема:** Рекомендация `type` = реальный URL на документацию, но если портала ошибок нет — будут битые ссылки.

**Решение:** Использовать URN-форму, не `about:blank`.

- `R-ERR-N` (Обязательно): «`type` — стабильный идентификатор класса ошибки. Допустимые формы:
  1. URL на резолвимую доку: `https://errors.example.com/order/not-found`
  2. URN: `urn:problem:<сервис>:<code>` — например `urn:problem:order-service:order-not-found`. Используется, если портала ошибок нет.»
- `R-ERR-X*` (Запрещено): «`about:blank` в `type` — теряется машиночитаемая категория ошибки. Используй URN.»

URN сохраняет структуру и позволяет клиенту матчить класс ошибки без deployment портала.

### 4.6. Граница `users/me`

**Проблема:** Когда `me` нужен, когда — фильтрация из токена молча.

**Решение:** Граница — может ли эндпоинт принять чужой ID.

- `R-ALIAS-N` (Обязательно): «`me` используется в эндпоинте, который МОЖЕТ принять и свой, и чужой ID (admin scope, OAuth-приложения). `me` явно фиксирует «текущий пользователь из токена».»
- `R-ALIAS-X*` (Запрещено): «`me` в эндпоинте, который по дизайну работает только с ресурсами вызывающего (например, `/profile`). Контекст из токена — единственный источник, `me` избыточен.»

Тест: «может ли супер-админ обратиться по другому ID?» Да → `me` нужен. Нет → не нужен, эндпоинт singleton (`/profile`, `/settings`).

## 5. Что НЕ меняем

- Смысл правил (за пределами 4.1–4.6).
- Порядок и количество секций.
- Внешние RFC-ссылки (RFC 9457, 7396, 5789, 8594, 6648, W3C Trace Context).
- Domain-language примеров (orders, users, payments) — гайд domain-agnostic.
