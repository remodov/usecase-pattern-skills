## Use Case Pattern skills

Проект использует методологию Use Case Pattern. Скиллы `ucp-*` и
style-guides установлены через `claude-code-java/install.sh`.

### Язык общения

Все ответы Claude в чате — **на русском**. Сюда же входят:
- планы от `superpowers:writing-plans` и их шаги;
- описания PR / коммит-сообщения;
- end-of-turn summary;
- комментарии в коде, если они нужны (но по правилам стиля комментарии
  пишутся редко — см. `.claude/docs/java-style-guide.md`).

**Технические термины и идентификаторы — на английском, как в коде:**
`UseCase`, `Handler`, `Controller`, `Aggregate`, `Bounded Context`,
`Domain Event`, `Repository`, `REST`, `Kafka`, имена классов / методов /
переменных / SQL-таблиц. Не переводим их в русский транслит.

Если пользователь явно пишет на английском или просит ответить на
английском — отвечайте на английском. По умолчанию — русский.

### Спецификация

Если в проекте есть `docs/spec/` — это источник правды по сервису.
Точка входа — landing-файл с frontmatter `type: service`, обычно
`docs/spec/00-<service>/<service>.md`.

Wikilinks вида `[[Name]]` (например `[[CreateProduct]]`,
`[[PRODUCT_NOT_FOUND]]`, `[[06-<service>-rules#BR-008]]`) резолвятся
поиском по `docs/spec/`:

```
find docs/spec -name "Name.md"
```

Per-item карточки имеют типизированный frontmatter (`type: command` /
`event` / `error` / `query` / `aggregate` / `integration`) — это
машиночитаемая часть спеки, ей можно доверять как контракту.

### Кодогенерация и ревью — через скиллы

Любая работа над UCP-артефактом **обязана** идти через соответствующий
`/ucp-*` скилл, а не писаться от руки. Это инвариант — без него код
дрейфует от методологии и review-скиллы будут ругаться.

| Тип работы | Скилл |
|---|---|
| Написать спеку по бизнес-описанию | `/ucp-spec-design` |
| UseCase + Handler + Controller + маппер | `/ucp-pattern-design` |
| OpenAPI + DTO + контроллер из карточки команды | `/ucp-api-design` |
| Spring Security + OAuth2 + ABAC + audit | `/ucp-auth-design` |
| Spring Boot bootstrap, Liquibase, jOOQ, профили | `/ucp-bootstrap-design` |
| Aggregate + VO + Domain Event + Repository (Tier C) | `/ucp-ddd-tactical-design` |
| Интеграционные / unit тесты по `15-*-acceptance.md` | `/ucp-test-design` |
| Ревью UseCase / Handler / Controller | `/ucp-pattern-review` |
| Ревью REST-контракта | `/ucp-api-review` |
| Ревью DDD-кода | `/ucp-ddd-tactical-review` |
| Ревью Java-стиля (то, что не ловит checkstyle) | `/ucp-java-style-review` |
| Ревью авторизации | `/ucp-auth-review` |

Style-guides — в `.claude/docs/` (Java, REST, DDD, auth, test, bootstrap,
usecase-pattern, usecase-spec-template).

### Интеграция с плагином superpowers

Если задача планируется через `superpowers:writing-plans` или исполняется
через `superpowers:executing-plans` — **план обязан называть конкретные
`/ucp-*` скиллы как шаги**, а не описывать их прозой («написать UseCase»,
«добавить ендпоинт»). Используйте таблицу маппинга выше.

Конкретно при планировании:

- Шаги плана формулируются как «вызвать `/ucp-pattern-design` для команды
  CreateProduct», а не «реализовать CreateProduct».
- Шаги ревью — отдельной парой к шагу design: «после `/ucp-pattern-design`
  → `/ucp-pattern-review` на изменённых файлах».
- Шаги тестирования — через `/ucp-test-design`, а не от руки.

При исполнении плана (`superpowers:executing-plans`): если текущий шаг
ссылается на ucp-* скилл, исполнитель **обязан** его вызвать, не
переписывать инструкции скилла словами.

Без этого правила superpowers строит размытые планы, обходящие
ucp-* — и review-скиллы потом ловят дрейф от методологии.

### Skill vs Agent — как запускать ucp-* скиллы

Все `/ucp-*` скиллы вызываются через **`Skill` tool в текущей сессии**
(или user-инициированной slash-командой `/ucp-...`). `Skill` инжектит
инструкции скилла в текущий контекст и переиспользует уже загруженный
style-guide и прогретый prompt-кэш.

`Agent` / `Task`-форк под ucp-скилл **запрещён**, в том числе для
прогона нескольких ревью-скиллов «параллельно». Причина:

- каждый форк стартует с холодным кэшем и перезагружает
  `.claude/docs/<style-guide>.md` заново;
- результаты форков не видят друг друга — общий контекст
  (уже прочитанный diff, уже найденные коды правил) не наследуется;
- параллельный fan-in трёх review-скиллов через Agent ≈ 3× токенов
  последовательного прогона через `Skill`, без выигрыша по качеству.

Прецедент: ревью фикса в двух файлах через три параллельных Agent-форка
съело ~570k токенов. Тот же набор скиллов последовательно через
`Skill` уложился бы в ~190k.

Исключение — когда форк нужен **по другой причине**: изолированный
worktree, длинный сторонний output, который не должен оседать в
основном контексте. Это сознательный trade-off, не default.

### Параллельные субагенты — когда да, когда нет

Если плагин предлагает разбить работу на параллельные субагенты
(`superpowers:dispatching-parallel-agents`,
`superpowers:subagent-driven-development`) — **разрешать только
для независимых задач, не связанных с ucp-* скиллами**. Для
design-цепочки, рефакторинга и прогона ucp-ревью — отказываться,
делать последовательно.

| Ситуация | Параллельно? |
|---|---|
| Тесты + линт + build одновременно | да |
| Fan-out по массиву однотипных правок (заполнить `severity` в 30 карточках) | да |
| Прогнать N ucp-ревью-скиллов на одном PR | **нет** — последовательно через `Skill`, см. раздел «Skill vs Agent» |
| Сгенерировать N агрегатов / команд / событий из спеки | нет |
| Цепочка `ucp-spec-design` → `ucp-pattern-design` → `ucp-test-design` | нет |
| Сквозной рефакторинг по нескольким файлам | нет |

Причина запрета на параллельный design: субагенты не видят прогресс друг
друга, контекст не общий — два UseCase, написанные параллельно, разойдутся
по стилю и именам. Это ровно та проблема, против которой UCP существует.

Параллельный режим хорош для **fan-out** независимых задач (тесты + линт,
правки в N карточках). Для **fan-in ревью** через ucp-скиллы — нет:
последовательный `Skill` дешевле и качественнее.

### Bootstrap на чистой машине

Если `.claude/skills/` пустой или в нём broken-симлинки — скиллы не
установлены. Выполните:

```bash
git clone https://gitlab.mosmetro.tech/common/claude-code-java \
  ~/IdeaProjects/claude-code-java
~/IdeaProjects/claude-code-java/install.sh .
```

После этого `.claude/skills/` и `.claude/docs/` будут симлинками на
upstream — обновления методологии прилетят автоматически на следующем
`git pull` в репо скиллов.
