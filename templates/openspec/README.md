# Шаблоны openspec

Заготовки под форму требований, описанную в
`.claude/docs/_meta/authoring-contract.md`. Копируются руками, ничего никуда
не устанавливаются.

| Файл | Когда берут |
| --- | --- |
| `domain-spec.md` | заводится новый домен корпуса — копируется в `.claude/docs/<трек>/<домен>/spec.md` |
| `requirement.md` | добавляется требование в существующий `spec.md` — вставляется блоком |
| `change/proposal.md` + `change/tasks.md` | изменение оформляется отдельным артефактом — каталог `openspec/changes/<id>/` |

`domain-spec.md` — валидный документ, а не набор скобок: он проходит
`spec_check` целиком, и тест `tools/tests/test_templates.py` следит, чтобы
проходил и дальше. Порядок работы с ним такой:

1. скопировать в каталог домена, каталог назвать так же, как область в **ID**;
2. заменить `example` на имя домена, текст — на свой;
3. завести `references/<lang>/`, если у домена есть код-примеры;
4. прогнать `python3 .claude/docs/_meta/spec_check.py`.

В `requirement.md` угловые скобки оставлены намеренно: он вставляется в живой
файл, где всё вокруг уже заполнено, и незаполненное поле должно бросаться
в глаза.

Имя гейта в примере взято из `_meta/project-gates.md` не случайно: собственная
проверка, которой нет в каталоге, роняет `spec_check`, а выдуманное имя правила
чужого анализатора не роняет ничего — и требование выглядит закрытым, не будучи
таким. Подставляя своё имя, сверьтесь с каталогом или с конфигом инструмента.

Форма пришла из `<репозиторий шаблонов фронтенда>` (`templates/next-ssr/openspec/`) —
там же живут требования frontend-трека. Отличие одно: у методологии нет своего
кода, поэтому поле **Гейт** называет вид проверки, а не `file:line`.
